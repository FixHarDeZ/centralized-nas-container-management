Date: 2026-10-08 (Asia/Bangkok)
Stack: `shorts-factory/`
Status: approved by the user on 2026-10-08; implemented and locally verified, not deployed.

## User outcome

หลังเลือก Topic และเขียน Script เสร็จ บอทส่งรายการคำที่ควรลองฟังเป็นพิเศษ
เพื่อช่วยตรวจตัวย่อภาษาอังกฤษ คำทับศัพท์ ชื่อเฉพาะ และชื่อรุ่นที่เสียง TTS
อาจอ่านรวบ สะกดผิด หรือแบ่งจังหวะแปลก ๆ รายการอ้างอิงคำใน Script รอบนั้น
และบอก Card ที่ต้องฟัง คนใช้แก้เสียงต่อด้วย `/say` และ `/redo` ได้เหมือนเดิม

รายการเป็นสิ่งที่ควรฟังตรวจจากข้อความ ไม่ใช่ผลตรวจไฟล์เสียงจริง
คำอ่านที่แสดงคือข้อความใน Script ไม่ใช่การยืนยันว่าเป็นคำอ่านที่ถูกต้อง

## Approaches considered

1. **Recommended: metadata in the existing Script response + local fallback.**
   โมเดลที่เขียน Script ระบุคำเสี่ยงและจับคู่กับ `spoken` ในคำขอเดิม
   โปรแกรมตรวจว่าคำอยู่ใน Card จริงและเก็บคำอังกฤษที่โมเดลตกหล่น
   ได้คำทับศัพท์ที่เขียนเป็นไทยแล้วด้วย เพิ่มขนาดคำตอบเล็กน้อยโดยไม่เพิ่มคำขอ
2. **Separate model analysis after generation.** รับรู้บริบทได้ แต่เพิ่มเวลารอ
   และต้องจัดการ timeout แยกใน flow ที่เขียน Script ใช้เวลาหลายนาทีอยู่แล้ว
3. **Rules only.** รวดเร็วและไม่เพิ่ม token แต่จับคำทับศัพท์ไทยและคำอ่านกำกวม
   ได้จำกัด ต้องคอยขยายพจนานุกรมให้ตามหัวข้อใหม่

## Review message

ส่งข้อความแยกทันทีหลังข้อความ Script เพื่อไม่ให้รายการถูกตัดด้วยเพดาน 4096
ตัวอักษรของ `format_script()` ข้อความ Script ยังคงถือ review keyboard และ
`state.message_id` ของตัวเอง ข้อความรายการไม่มีปุ่ม และไม่เขียนทับ message id

ตัวอย่าง (คำอ่านตัวอย่างเป็นข้อความจาก Script):

```text
🎧 คำที่ควรลองฟัง — ทำไมคอมช้า

• CPU → ซีพียู
  card 2, 4 · ตัวย่อ: ฟังว่าสะกดครบและไม่รวบเสียง
• Docker → ด็อกเกอร์
  card 3 · คำทับศัพท์: ฟังจังหวะและเสียงท้ายคำ
• GPT-4 → จีพีทีโฟร์
  card 5 · ชื่อรุ่น: ฟังตัวย่อและเลขรุ่นติดกัน

รายการนี้คัดจากข้อความ ยังไม่ได้ตรวจเสียงจริง
เสียงเพี้ยน: /say <คำอ่านที่ผิด> = <คำอ่านที่ต้องการ> แล้ว /redo
```

ใช้ Card 1 เป็น hook และนับ Card อื่นจาก 1 ให้ตรงกับข้อความรีวิว
รวมคำที่ซ้ำกันและมีคำอ่านเดียวกันเป็นหนึ่งรายการ พร้อม Card ทุกตำแหน่ง
หากคำเดียวกันใช้คำอ่านต่างกัน ให้แสดงแยกเพื่อให้คนใช้เห็นความไม่สม่ำเสมอ
เรียงตัวย่อ/ชื่อรุ่นก่อน ชื่อเฉพาะแล้วคำทับศัพท์ แต่แสดงรายการที่พบทั้งหมด
หากยาวให้ใช้ `say()` ที่ chunk ข้อความอยู่แล้ว ไม่ตัดรายการทิ้งเงียบ ๆ

เมื่อไม่พบให้แสดงว่า "ไม่พบคำที่เข้าข่ายในข้อความ — ยังควรฟังคลิปก่อนอัปโหลด"
ไม่ใช้คำว่าเสียงถูกต้องหรือผ่านการตรวจเสียง

## Data and extraction

เพิ่ม optional `pronunciation_checks` ต่อ Card ในผล JSON ของโมเดล:

```json
{
  "narration": "ลองเช็ก CPU ก่อนเปิด Docker",
  "spoken": "ลองเช็กซีพียูก่อนเปิดด็อกเกอร์",
  "pronunciation_checks": [
    {"term": "CPU", "spoken": "ซีพียู", "kind": "acronym"},
    {"term": "Docker", "spoken": "ด็อกเกอร์", "kind": "loanword"}
  ]
}
```

- `term` ต้องเป็น substring ของ `narration` ของ Card นั้น โดยไม่สนตัวพิมพ์ใหญ่เล็ก
  และ `spoken` ต้องเป็น substring ของข้อความ `spoken` ที่ Card ใช้จริง
  คำทับศัพท์ที่ narration เขียนเป็นไทยแล้วใช้คำไทยนั้นเป็น `term` ได้
- `kind` เป็นหนึ่งใน `acronym`, `loanword`, `proper_name`, `model_name`
  เหตุผลที่แสดงใช้ข้อความไทยสั้น ๆ ตามประเภท เพื่อไม่ให้โมเดลแต่งคำอธิบายยาว
- วิเคราะห์เฉพาะคำที่พูดจริงใน `narration`/`spoken` ไม่ดึงจาก `query`,
  title, description, hashtags, code หรือข้อความบนจอที่ไม่ได้พูด
- Metadata ไม่ครบหรือผิดรูปให้ข้ามรายการนั้นแล้วใช้ fallback ไม่ทำให้
  Script ที่ valid อยู่แล้วถูก reject หรือเสีย model retry
- Fallback ของคลิปไทยดึงคำละตินจาก `narration` รวมตัวย่อแบบมีจุด
  ชื่อผสมตัวเลข/ขีด และวลีชื่อที่มีหลายคำตามรูปแบบที่ตรวจได้
  หากไม่มีคู่คำอ่านที่เชื่อถือได้ แสดงข้อความ `spoken` ของ Card เป็นบริบท
  พร้อมบอกว่าต้องตรวจการจับคู่ ไม่เดาคำอ่านหรืออ้างว่ารู้คำอ่านของคำนั้น
- คลิปอังกฤษใช้ metadata แบบเดียวกัน เน้นตัวย่อ ชื่อเฉพาะ ชื่อรุ่น และคำอ่านกำกวม
  Fallback จับตัวย่อ/ชื่อผสมเลข ไม่ดึงทุกคำอังกฤษเป็นรายการเสี่ยง
- Metadata ที่ normalize แล้วเก็บอยู่ใน Script ซึ่ง `manifest.add_script()`
  และ state เก็บอยู่แล้ว ไม่เพิ่ม DB หรือ schema version ใหม่
  Script เก่าที่ไม่มีฟิลด์นี้ยังอ่าน/render ได้ และสร้างรายการด้วย fallback ได้

แยก logic normalization/extraction/formatting ไว้ใน `app/pronunciation.py`
ให้รับ Script + Locale และใช้ stdlib ไม่เพิ่ม dependency หรือ import
Pillow/edge-tts เข้ามาในโมดูลนี้

## Pipeline behavior

- Topic ที่พิมพ์เอง ปุ่ม trends และ auto-pick เข้า `make_script()` เดียวกัน
  ส่งรายการหลัง Script สำเร็จและ normalize ก่อนเก็บ Manifest
- แก้ Script สำเร็จให้สร้างรายการจากรอบใหม่แทนรายการรอบก่อน
  หากแก้ไม่สำเร็จและคืน Script เก่า ใช้รายการของ Script เก่านั้น
- รอบอัตโนมัติส่งรายการด้วย แล้ว render ต่อได้เหมือนเดิม
  ระหว่าง await ส่งรายการให้คงโหมด busy เพื่อไม่ให้คำสั่งใหม่เริ่มแก้ Script ซ้อน
  การส่ง checklist ล้มเหลวไม่ทำให้ Script สูญหาย ไม่ค้างโหมด และไม่หยุด render
- `/both` สร้างรายการตาม Script และ Locale ของแต่ละครึ่ง
- รายการข้อความแยกคงอยู่เมื่อ `do_render()` ปลดปุ่มรีวิว
  การแก้ render, storyboard และ `/redo` ใช้กลไกเดิม
- บรรทัดคำอ่านระบุชัดว่าเป็นคำใน Script ส่วน `/say` อาจแทนที่ตอน render
  ใส่หมายเหตุสั้น ๆ ให้ดู `/say` สำหรับ override ที่ตั้งไว้
  รายการไม่แก้คำอ่านหรือไฟล์ override อัตโนมัติ

## Scope

รอบนี้เพิ่มรายงานใน Telegram และเก็บ metadata ใน Script เท่านั้น
ไม่เพิ่ม audio preview, timestamps, ปุ่มยืนยันการฟัง, automatic `/say`,
การตรวจเสียงด้วย speech recognition หรือส่วนแสดงผล dashboard ใหม่
ไม่เปลี่ยน prompt เนื้อเรื่อง เสียง TTS การจัดวรรค หรือกติกาอัปโหลด
นอกจากเพิ่มกฎ/ตัวอย่าง JSON สำหรับรายการคำที่ควรฟังตรวจ
