## Architecture

Two containers in the stack:
- **hermes-gateway** — from `hermes-agent` image, runs `hermes gateway run`; connects Telegram + Discord, processes messages
- **hermes-dashboard** — from `hermes-agent` image, runs `hermes dashboard`; exposes `5063:9119` with built-in basic auth

Auth is injected via `scripts/inject-dashboard-auth.sh` wrapper (reads `DASHBOARD_PASSWORD_HASH` from vault-seeded env var).

Persistent volume: `hermes_agent_data:/opt/data` — config, sessions, memories, skills, logs

### Dashboard Auth (v2026.7.1+)

Hermes v2026.7.1 requires auth providers when binding to non-loopback addresses. The `--insecure` flag no longer bypasses this. Solution: `scripts/inject-dashboard-auth.sh` wrapper reads env vars and injects `dashboard.basic_auth` into `config.yaml` before s6 starts.

| Vault Key | Env Var | Purpose |
|-----------|---------|---------|
| `stacks.hermes_agent.dashboard.basic_auth_user` | `DASHBOARD_BASIC_AUTH_USER` | Username (default: `fixhardez`) |
| `stacks.hermes_agent.dashboard.password_hash` | `DASHBOARD_PASSWORD_HASH` | scrypt hash for hermes dashboard auth |
| `stacks.hermes_agent.dashboard.basic_auth_password` | — | Plaintext password (vault only, not in .env) |

Login credentials: see vault (`stacks.hermes_agent.dashboard.*`)

### Critical: HERMES_HOME

`HERMES_HOME=/opt/data` must be set in docker-compose.yml environment for both containers.  
Without it, hermes falls back to `~/.hermes` (ephemeral, not the volume) and loses config on restart.

### Model + Tune Config (config.yaml)

Live `/opt/data/config.yaml` is generated by hermes (full schema dump, ~13.8 KB). The repo's `config.yaml.example` documents the minimal **overrides** we apply on top — model selection plus the 2026-06-02 token tune.

`model:` is a mapping pointing to provider details:

```yaml
model:
  default: "mimo-v2.5-pro"     # current production; locked by user choice
  provider: "xiaomi"
  base_url: ""
```

Post-2026-06-02 token tune (verified keys in `hermes-v2026.5.16-schema.md`):

```yaml
session_reset:
  mode: both
  idle_minutes: 15             # was 1440 default — zombie sessions broke prefix cache

agent:
  max_turns: 20                # was 60 — cap iteration runaway
  api_max_retries: 1           # was 3 — faster failover
  image_input_mode: text       # was auto — pre-analyze images, kill vision tokens

memory:
  memory_enabled: false        # was true — 1-week trial; primary cache fix
  user_profile_enabled: false  # was true — same mechanism

compression:
  threshold: 0.80              # was 0.50 — delay context rewrite

delegation:
  max_concurrent_children: 2   # was 10 — 2026-11-05: each subagent call spawns a claude node process
                               # (subscription plugin) + heavy tool work; 3-way fan-out hung the NAS
```

Set via `hermes config set <key> <value>` in the container — hot-reloaded (cache keyed on file mtime/size).

## Known Gotchas

- **`HERMES_HOME` must be in docker-compose env** — entrypoint sets it locally but doesn't export to child `hermes` binary; falls back to `~/.hermes` (ephemeral) without explicit env
- **`model:` must be a mapping** — setting `model: <slug>` as scalar + indented sub-keys (default, provider) is invalid YAML; causes "No models provided" HTTP 400 from OpenRouter
- **Session reset key is `session_reset.idle_minutes`** — NOT `session.reset_on_idle_minutes` (a guess that hermes silently ignores). Default 1440 (24h) means sessions persist all day unless overridden. See `hermes-v2026.5.16-schema.md` for full key list.
- **Memory keys are `memory.memory_enabled` + `memory.user_profile_enabled`** — both inject mutable content into system prompt every turn, destroying upstream prefix cache when on. Off for 1-week trial through 2026-06-09.
- **`docker compose restart` can leave orphan s6-log lock** on the volume → next start crash-loops with `s6-log: fatal: unable to lock /opt/data/logs/gateways/default/lock: Resource busy`. Fix: full stack `down` + `up -d` releases the lock.
- **Telegram logs success at INFO level** — only failures appear as WARNING/ERROR in docker logs; silence = success
- **Discord error is expected** — `ERROR: No bot token configured` is normal if Discord not used
- **`.htpasswd` permissions matter** — keep `nginx/.htpasswd` readable by nginx worker (`644`); deploy script already normalizes this on NAS
- **uv-managed Python must live outside `/root`** — v2026.8.18 needs Python 3.11 while the Debian 13 base ships 3.13, so `uv sync` downloads its own interpreter. uv's default install dir is under `/root` (mode 0700), which the non-root `hermes` user can't traverse → `exec .venv/bin/python: Permission denied`, exit 126 crash loop on both containers. Fixed with `ENV UV_PYTHON_INSTALL_DIR=/opt/uv-python` + `chmod -R a+rX /opt/uv-python`
- **`deploy.sh` needs `-y` when non-interactive** — its `Upload now? [y/N]` prompt reads nothing, skips the upload, and still exits 0; the next `--build` then rebuilds the stale remote Dockerfile entirely from cache (same image sha) and looks like the fix didn't work
- **v2026.7.1+ requires auth providers** for non-loopback dashboard binds — `--insecure` no longer bypasses. Fixed via `inject-dashboard-auth.sh` wrapper + vault-seeded env vars
- **DSM RP `:15063` needs the WebSocket custom header** — Chat tab (`/api/pty`, `/api/ws`, `/api/events`) is all WebSocket; entry without `Upgrade`/`Connection` = endless "Chat connection interrupted. Reconnecting..." while HTTP pages work. Also raise RP read timeout above 60 s. Verify: WS handshake via RP must give 403 (app gate), not 401 (plain GET)
- **Dockerfile must set `HERMES_TUI_DIR=/opt/hermes/ui-tui` (+ `HERMES_NODE=/usr/local/bin/node`)** — without it the Chat tab terminal checks bundle freshness with PM's Node in `/opt/data/tools` (newer than the image's node 22), decides the bundle is stale, runs `npm ci` in `/opt/hermes` as uid 1000 → EACCES → `/api/pty` dies right after `pty accepted`, reconnect every ~3 s. Upstream Dockerfile sets the same var; re-check upstream's `ENV` block on every `HERMES_REF` bump
- **hermes-gateway must stay memory-fenced (`mem_limit` + `memswap_limit` equal, 4g)** — every tool process (`claude -p` children, ffmpeg, faster-whisper) lives in its cgroup. 2026-11-05 a 3-task async delegation swap-thrashed the whole 12 GB NAS: no oom-kill in kern.log, ping/TCP alive but SSH banner + nginx dead, power cycle needed. Early warning in `agent.log`: `kanban dispatch: system memory pressure is elevated/critical`. `mem_limit` alone is not enough (overflow goes to swap). DSM cgroup v1 honours memsw — verify via `/sys/fs/cgroup/memory/docker/<id>/memory.memsw.limit_in_bytes`
- **Node version follows upstream `engines`** — tag `.npmrc` has `engine-strict=true`; v0.22.7 needs node ≥26 (`node_source` pinned to upstream `pm/lock.json` node). Node 25+ images have **no corepack** (only npm). `update-hermes.sh` preflights `engines.node`; check bundled npm vs `engines.npm` by hand
- **v0.23.1+ builds with pnpm, not npm**: `engines.npm` refuses npm; the root preinstall accepts only the pnpm pinned in `pm/lock.json`. Our Dockerfile stages it via upstream's `pm` one-liner, then `scripts/build/node-deps.mjs` → `tui.mjs`/`web.mjs` (products replace `ui-tui/` and `hermes_cli/web_dist`). `update-hermes.sh` preflights a package-manager mismatch. Test-build a new tag through a throwaway compose project (`docker build` on DSM is the legacy builder, no `COPY --chmod`)
- **v0.23.1 core ignores `session_reset`** (only /new or /reset end a conversation). Our idle-15 policy lives on through the catalog plugin `hermes-session-reset-policy` (keep it enabled after rebuilds; the volume keeps it in `/opt/data/plugins/`)
- **venv interpreter = pm-pinned Python** (`/opt/hermes-python` → `/opt/pm-build/tools/python-<pin>`): uv's own download (python-build-standalone) links SQLite **statically**, and 3.14.4 carried 3.50.4 with the WAL-reset bug, so a rebuilt libsqlite3.so (upstream's approach for Debian python) would not reach it. The build refuses SQLite <3.51.3. Re-check `pm/lock.json` python on every bump
- **Old sessions store model per-session** — sessions created before config fix have empty model; new sessions use config

## Shopee clip skills — repo-owned since 2026-11-10

`hermes-agent/skills/{shopee-clip,flow-driver,gameplay-clips}` → `make hermes-skills` (pull clone in container
+ `skills/sync.sh`: copy tracked files, `hermes curator pin`). **Not locked**: `hermes curator lock`'s terminal
heuristic refused a legit pipeline command and stalled a real clip (2026-11-10). In-place edits are saved to
`/opt/data/clips/skill-drift/<ts>/` (+diff) on the next sync, then overwritten. **To keep them:
`make hermes-skills ARGS=--pull`** (copies live drift into Hermes' clone, changes nothing live) → review, commit,
push → sync. Hermes also ports its own edits (it pushed `ff2a98f` itself on 2026-11-12). `sync.sh` refuses a dirty
clone and is test-gated (`DOC_BUDGETS`: router ≤15 KB, house-rules ≤20 KB, gameplay SKILL ≤30 KB, flow-driver ≤8 KB).
Runtime data: `/opt/data/clips/jobs` (clipjob state), `/opt/data/clips/logs` (clip-log, delivery-log, perf-log),
`/opt/data/clips/flow-state` (Flow project roster/edit ids), `/opt/data/clips/work/<job>` (durable job workdir —
scratch is pruned ~24 h). Old skill archived at `/opt/data/skills-archive/flow-shopee-clips`.
Flow: Q1 mode (🎬 footage from official videos — games + brand product films / 🧑 presenter+graphic / 📦 graphic ล้วน;

checklist) → Q3 📝 prompt pack / 🤖 auto (auto falls back to 📝 itself) → `clipjob.py ready/decide` per shot → post
(graphics always) → `clipjob.py deliver` (only send path; clip + ONE copy-button message + cover). **🎬 also runs
through clipjob since 2026-11-12**: `new --mode gameplay`, `note` per stage, `deliver` (no report needed;
`--style footage` for brand films), `reopen` for a revision (REVISED row).

id, `edit-id` records the real one; a failed paid shot sends its own 🔁 button; `ready --resend`; `reserve --wait`
