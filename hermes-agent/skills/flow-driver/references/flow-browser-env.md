## Environment
- Chrome on Xvfb :99, CDP http://127.0.0.1:9222, profile /opt/data/browser-profiles/chrome-flow (Google logged in, Flow PRO). Read the live balance from the avatar menu: click the avatar (≈(1219,37) at 1280 px), which shows `N Google Flow credits`. Quote that number, never a remembered daily quota.
- **CDP is usually DOWN when a session starts** — `browser_exec` fails with `BU_CDP_URL … unreachable`. Cold-start it with the `browser-automation` §1 recipe pointed at this profile: `Xvfb :99` (background) then `DISPLAY=:99 /opt/data/tools/chromium-1208/chrome-linux64/chrome --no-sandbox --disable-gpu --disable-dev-shm-usage --window-size=1280,900 --remote-debugging-port=9222 --user-data-dir=/opt/data/browser-profiles/chrome-flow --no-first-run https://flow.google.com/` (headful on Xvfb, NOT `--headless`; see the `unusual activity` section), started via `terminal(background=true)` (`nohup`/`disown` wrappers are rejected by the tool). Ready = `curl -s http://127.0.0.1:9222/json/version` prints `Browser`. **`--no-sandbox` is mandatory here** — without it Chrome aborts with a sandbox FATAL before CDP ever opens, which looks like a broken launch rather than a missing flag. **`--disable-gpu` (and `--disable-dev-shm-usage`) is ALSO mandatory (learned 2026-10-22): without it the launch comes up with browser-level CDP fully answering while EVERY tab's renderer is wedged.** `Target.getTargets`, `Target.attachToTarget` and `Page.reload` all reply fine, but every `Runtime.evaluate` times out at 5 s — on every tab including a freshly created one — so it misreads as 'the Flow SPA is slow to boot' when it is a dead renderer. Log signature: `ContextResult::kTransientFailure: Failed to send GpuControl.CreateCommandBuffer` plus `vkCreateInstance: Found no drivers`. Diagnostic rule: browser-level CDP alive + all renderers dead = missing `--disable-gpu`, NOT a slow page — stop waiting out the timeouts and relaunch with the flag. `--headless=new` renders the DOM, but its `HeadlessChrome` UA gets every submit rejected (see the `unusual activity` section), so launch headful. Without `--window-size` **the viewport width is not stable across launches**: it has come up at ~800 px (narrow picker) and ~1700 px (desktop picker). `--window-size=1280,900` gives the desktop popover layout. Always read `page_info().w` and branch; never carry selectors over from the previous session. See Layout detection below and `references/flow-picker-dom.md`.
- **Lifecycle — Fix's standing instruction: close Chrome once the clip is delivered** ("งานหน้าจะได้ไม่ต้อง kill เปิดใหม่ทุกรอบ"). Do it as the LAST act of a finished pipeline, never mid-run: killing Chrome between attaching and submitting throws away the ingredient chips, which are page state, so an interrupted session should leave Chrome running and say so, letting the next session resume with `page_info()` and reuse the browser as-is instead of relaunching. Close it with CDP `Browser.close` (see the `unusual activity` section for why pkill is the wrong close).
- Drive via browser_exec: js(), cdp(), click_at_xy(), capture_screenshot()+vision_analyze for DOM-blind states. A browser_exec session attaches to `about:blank` on its first call, so `page_info()` and `js()` read the blank tab until you run `new_tab(<project url>)` (plus `wait_for_load()`); do that before any DOM query.
- **A browser_exec call is cut at ~420 s wall clock regardless of `timeout_s`** (a 1500 s poll loop died at 420 s). Keep each poll loop under ~360 s and call again; a cut loses Python state but Chrome and the chips survive, so re-run the state probe before assuming anything.
- **A stale `SingletonLock` naming a DEAD pid blocks the launch outright**: Chrome exits with `The profile appears to be in use by another Chromium process (<pid>) on another computer` and CDP never opens, while `ps -o pid,args -p <pid>` returns only a header (pid gone). Fix: delete `/opt/data/browser-profiles/chrome-flow/Singleton{Lock,Socket,Cookie}` and relaunch — do not chase the "other process" the message names. Same for `pgrep` hits on the launch pattern that are really the terminal wrapper's own argv: prove liveness with `ps`, never pgrep (see step 12).
- **Give every launch its own log path, spawn Chrome DETACHED from the tool call, and probe `curl -s http://127.0.0.1:9222/json/version` before attaching.** Reusing the previous run's log makes a dead launch indistinguishable from a live one (it still shows the OLD run's output while the port answers nothing), and a Chrome started under a tracked background shell has vanished mid-pipeline with no fatal line in its log — the first symptom is `page_info()`/`Runtime.evaluate` failing on a browser that answered a minute earlier, so re-probe the port before blaming the page. Detached launch that survives the call (shell `nohup`/`setsid`/`disown` wrappers are rejected by the terminal tool): one foreground `execute_code`/`terminal` call running `python3 -c "import subprocess,os; subprocess.Popen(['<chrome>','--no-sandbox','--disable-gpu','--disable-dev-shm-usage','--window-size=1280,900','--remote-debugging-port=9222','--user-data-dir=/opt/data/browser-profiles/chrome-flow','--no-first-run','https://flow.google.com/'], stdout=open('/opt/data/cache/scratch/<fresh-name>.log','w'), stderr=subprocess.STDOUT, stdin=subprocess.DEVNULL, start_new_session=True, env={**os.environ,'DISPLAY':':99'})"` — `start_new_session=True` is what detaches it — then readiness-check in a separate call.
- **Two `Settings` controls exist and only one of them sets generation options.** The header `Settings` button
  opens view preferences (Grid/Batch, grid size, clear-prompt-on-submit) — no Video, no Length, no credits line
  in it. The prompt bar's `Settings trigger` opens Image/Video, aspect, model, resolution, the Length slider and
  `Generating will use N credits`. Make those changes BEFORE typing the prompt (rule below), set Length by
  writing the slider's value through the native value setter plus `input`/`change` events (its value is an index,
  not seconds — 3 → 6s, 5 → 8s, 7 → 10s), and read the result back from the panel's own `N Sec` + credits line,
  never from the number you set. **When the panel does NOT follow — the `N Sec` text lags several interactions
  behind the input, arrow keys and track clicks no-op, and reads race each other — stop poking the slider: write
  `localStorage['flow-prompt-box-settings']` (JSON, set `videoDuration` to the seconds) and `location.reload()`;
  the trigger then reads `Video · 720p · <N>s` again.** A slider sweep can leave the project at a DIFFERENT
  duration than it started (15 s = 60 credits), so after ANY duration interaction — probe or fix — re-read the
  trigger string and the `Generating will use N credits` line before `reserve`: only a number read on screen may
  go on a board or be spent.
- Prompt editor = div.ProseMirror (may lack data-placeholder): **focus it before typing** — `p.focus()` + select its contents + `execCommand('delete')` to clear, then `cdp('Input.insertText', text=...)` **in ~700-char chunks split on newline boundaries** (`chunk.rfind('\n')`), reading `innerText.length` against `len(PROMPT)` plus a head/tail slice after every pass. An insert into an UNFOCUSED editor lands only its first line (93 of 1,979 chars) while reporting ok, and an insert whose caret sits at position 0 splices the new text BEFORE what is already there — both read as a working prompt unless you check length AND head/tail. ~1,600 chars in one call is not a guarantee; chunking is. **`cdp(...)` is a Python helper inside `browser_exec`, NOT a JS function** — writing it inside `js("cdp('Input.insertText', …)")` dies with `ReferenceError: cdp is not defined` before any text is typed, which reads like a broken editor. Call it from Python; keep `js()` for DOM reads and dispatches.
- **Typing the prompt: ONE full-length `cdp('Input.insertText', text=PROMPT)` beat chunking outright (2026-10-28).** The ~700-char chunk loop reported healthy lengths after each pass (636 → 665 → 674 → 499) while each new insert was REPLACING the whole document instead of appending — the final text was the last chunk only, ~494 of 2,443 chars, and the read-back length per chunk is what caught it. Clearing to an empty editor first, then a single insert, produced innerText whose whitespace-normalised form compared EQUAL to the source file (2,435 = 2,435) on the first try — so try the single insert, verify with `re.sub(r'\s+',' ',text)` equality against the file, and only fall back to chunking if that comparison shows truncation (then re-place the caret at the end before each pass and abort the moment a length shrinks). **Never compare raw `innerText.length` between two reads — it drifts by a few dozen chars as trailing newlines collapse, so a raw mismatch against the file on a normalised-equal prompt is not truncation; the normalised comparison is the only verdict.**
- **When the DOM is driven through the stateless `browser_cdp` tool you cannot read the prompt file from Python, so hand the file's BYTES to the page instead of re-typing Thai into a tool parameter** (a parameter you retype is a transcription you can get wrong, and the prompt must reach Flow byte-identical to the approved `shot<K>.txt`). `base64 -w0 <workdir>/shot<K>.txt` in `terminal`, then ONE `Runtime.evaluate` that does everything in-page: resolve the live `div.ProseMirror` by rect, `pm.focus()`, `selectNodeContents(pm)` + `execCommand('delete')` to clear, `const text = new TextDecoder('utf-8').decode(Uint8Array.from(atob(b64), c=>c.charCodeAt(0)))`, then `document.execCommand('insertText', false, text)` — a contenteditable insert drives ProseMirror's input handling the same way `Input.insertText` does, and it works because the editor was already empty. Verify with the normalised comparison as above, but compute the FILE's normalised length in Python first (`re.sub(r'\s+',' ',t).strip()`): the raw page length and the file length differ by the collapsed newlines, so only the normalised pair is a verdict, and a match there proves no truncation and no drift. **Driving the Flow tab from `browser_exec`'s own tab (`new_tab(<project url>)`) skips the base64 step entirely:** its Python can `text = open(<workdir>/shot<K>.txt).read()` and pass that string straight into `cdp('Input.insertText', text=text)` — byte-exact, no blob crossing a tool boundary, same normalised verification; only the `/json/*` probes still belong in `terminal`, because its urllib to 127.0.0.1 is refused.
- **`selectNodeContents(pm)` + `execCommand('delete')` wipes the ingredient CHIPS too, not just the text.** Chips live inside the same prompt box, so a clear-then-retype cycle silently drops them: the box read `chips: 0` after typing even though two chips had just been attached. Order that avoids redoing work: type the prompt FIRST, then attach image + character, then submit. The rule behind that order is that a CLEAR is the only forbidden move — attaching first and then inserting into an ALREADY-EMPTY editor keeps every chip too (no second attach cycle), fine as long as you read `chips` back after the insert to prove nothing was dropped — and if a clear is unavoidable, verify `chips` afterwards and re-attach (no re-upload needed) before hitting Start generation. A pre-submit check of `chips == expected` and normalised-text equality is cheap and catches both failure modes at once — but it goes STALE the moment you touch the Settings trigger or send Escape: those panel interactions can empty the live box (prompt back to length 1, chips 0) with no error of their own, so any check older than your last panel interaction proves nothing. Recovery costs zero credits: retype into the now-empty editor (single insert + normalised equality) and re-attach from Uploads (no re-upload), then re-run the whole gate. Order the run so this never fires: make EVERY Settings change (model, duration, resolution) BEFORE typing the prompt — an Escape from the settings panel has emptied a FILLED box (prompt AND chips) outright, so once Settings opens, treat the box as unsafe until you have re-read it.
- **`js()` must return plain values** (strings, numbers, arrays, objects of primitives). Returning a DOM element from the expression fails with `Object reference chain is too long`; return `.innerText.length`, a `{x,y}` rect or the `aria-label` string instead.
- **Keep regexes and Thai text OUT of `js()` — return the raw string and filter in Python.** A JS regex literal carrying Thai or a `[^\n]` class dies at parse time with `SyntaxError: Invalid regular expression: missing /` (the escapes do not survive the tool boundary intact), which reads like a broken page rather than a bad pattern; and element leaf-queries over a whole overlay can hit nodes with no `innerText` (SVG) — `Cannot read properties of undefined`. Return `e.textContent || ''` / the full `innerText` and do the matching in the Python side, where the string is verbatim.
- **`js()` takes no data argument** — its second positional parameter is the CDP `target_id`, so `js(expr, value)` dies with `No target with given id found` and the value never reaches the page (it reads like a dead tab, not a bad call). Inline the data into the expression string instead; keyword args belong to `cdp()`, never to `js()`.
- **Never shadow a Python builtin inside `browser_exec` code** — the harness `exec`s your code in its own module globals, so a variable named `len` / `str` / `id` overwrites the builtin the harness's own output writer calls, and the whole call dies with an opaque `TypeError: 'list' object is not callable` raised inside the harness before any result comes back (it reads like a broken page). Name such variables `n`, `total`, `cnt`.
- Inside `browser_exec` you get plain stdlib Python only: `hermes_tools` is NOT importable there (different interpreter), so read prompt/asset text with `open(path).read()`, not `hermes_tools.read_file`. The pre-imported helper module can also be absent: when `import agent_helpers` raises `ModuleNotFoundError`, import the identical helpers from the harness itself — `from browser_harness.helpers import new_tab, goto_url, page_info, js, cdp, click_at_xy, capture_screenshot, ensure_real_tab, wait_for_load`.

- **A chip's name is not proof of its image** (a uniquely named upload once resolved to another product's photo — a
  baby-wash bottle came back for the frame). **Verify every chip by PIXELS, not vision (Fix 2026-11-23):** crop the

  `uv run --with pillow --with numpy python -I scripts/chipcheck.py --shot <img> --rects '<json>'` (rects = the
  chips' CSS px; a `cdp_shot.py <out> X Y w h S` crop adds `--origin X,Y --scale S`)
  (or `--chip <crop>` per chip) `--expect <file>` repeated once per file that must be in the box (refs, the character portrait /opt/data/clips/characters/<name>.jpg, the start frame), then `--pool-dir /opt/data/clips/characters [--pool <other
  colourway / earlier product>]`. A chip is the file's centre square (`object-fit: cover`), so the match is
  measured: real chips scored 0.95–0.98 against their file, the next candidate ≥0.2 lower (genme shirt/duck/น้องเนย,
  plaid colourway). Exit 0 = verified, no vision; exit 1 = a WRONG / no-match / missing chip — fix the attach
  (cancel icon, re-attach) and rerun, no vision; exit 3 = runner-up too close — ONE vision read of that chip
  only; exit 4 = no chip matched anything = the CAPTURE is off (origin/scale, box scrolled): re-capture, never
  touch the chips or log `trouble`. A no-match chip is a stray from an earlier clip or a file you did not list
     (start frame).
     **`doubled` / both chips scoring the same file is a TIE, not proof of a wrong attach, when the expected refs are near-identical variants of one product** (two flavours of the same box, two colourways of one shirt): the centre square both chips are scored on is dominated by the shared design, so the match collapses onto whichever file it tries first and exit 1 fires on a CORRECT attach. Settle it with evidence the centre square cannot fake — the two chips' `img.src` strings and `naturalWidth`/`naturalHeight` differ (Flow resizes each upload to fit, so two distinct uploads of different-aspect crops give different dimensions) — plus your own chip×ref matrix in Python (every chip against every expect file, centre square, same normalised MSE): when each chip's own best is a DIFFERENT file, the attach is right and no re-attach happens. Only a duplicate `src` (or a matrix where both chips clearly prefer one file AND the dimensions match) earns the cancel-and-re-attach.
     Flow re-encodes
  uploads, so a sha256 of fetched chip bytes never equals the source: never hash-compare. Fetching `img.src`
  works for product chips only (a character chip's `flow.google.com/asb/...` URL answers HTML) — the screen
  crop serves both.

- **Screenshots can time out while the DOM is healthy.** On headful Xvfb, `Page.captureScreenshot` hit a 30 s timeout while `Runtime.evaluate` answered in milliseconds on the same tab. ## `unusual activity` Failed cards — headless UA, then submit bursts
- **`--headless=new` sends `User-Agent: HeadlessChrome/…`.** Check it with `curl -s :9222/json/version`. With that UA every submit dies on a `Failed` card reading *"We noticed some unusual activity. Browser extensions that modify the page may cause issues"*, even though the Google account is in good standing. The fix is to relaunch **headful on Xvfb** (recipe in Environment). The UA then reads plain `Chrome/…` and submits render. Check the UA before the first submit of every run, because one Failed card costs a full chip-attach cycle.
- **Kill Chrome in a terminal call of its own.** `pkill -f '[c]hrome-flow'` also kills the tool's own shell when that same command line contains the literal path (`rm …/chrome-flow/Singleton*`), because `-f` matches the shell's argv. The call then dies with SIGTERM. Run the pkill alone, then do the lock cleanup in the next call (`cd /opt/data/browser-profiles && rm -f chrome-fl*/Singleton*`).
- At 1280 px the project loads in **agent-panel layout**. Close the panel (✕ top right), then use the bottom `flow-prompt-box`. Turn the `Agent` chip OFF: it is `button.agent-mode-chip`, and `-checked` means on. The desktop picker is `flow-add-menu-popover-content`. Click a row, then press its `Add to prompt` button, and the popover closes after each add. The newest tile's `Download` button downloads 720p directly into the `setDownloadBehavior` dir with no menu.
- **Manual mode is the response to the FIRST `unusual activity` card (Fix's rule 2026-11-09).** Do not retry, clear cookies, relaunch or re-login first. On the shelf run, a cookie clear plus re-login let exactly one shot through (shot 1). Shot 2 failed again 7 h later in a fresh session, while every shot Fix pasted into his own browser rendered first time. Close Chrome with `Browser.close`. Then, per remaining shot, send: the ref image as `MEDIA:` + exact chips (H = product only; P/R = product + the named character) + `9:16 · 720p · <N>s · x1` + the prompt in one code block. Hand out one shot at a time and QC each returned mp4 (ffprobe + 2 frames + the presenter-identity check in `frame-check.md`) before handing out the next. Copy each one into the job dir, because native-inputs is not durable. Then run post as usual. **Keep shotboard in the loop in manual mode too.** Fix's render counts as the submit: call `submitted <job> <k> --edit-id manual-<k>`, then `ready` with his file so he gets the gates and the review buttons, and finish with `assemble-check` and `close`. The shelf run skipped shotboard entirely, so it had no record, no gates and no buttons.
- **A headful browser trips it too on a submit burst.** Four renders submitted back to back within about 10 min were followed by two `unusual activity` Failed cards, 90 s apart. On a multi-shot board, pace the submits (do not fire the next one the moment the previous render lands). After one retry, stop and report with the zero-credit options. Unlike the generic `Something went wrong` card (pitfalls.md), this one is a rate or risk signal, so retrying in a loop deepens it.
- **What it actually is (measured 2026-11-09):** Flow loads **reCAPTCHA Enterprise v3** (`grecaptcha.enterprise`, invisible score-based key `6LdsFiUsAAAAAIjVDZcuLhaHiDn5nnHVXVRQGeMV`), and `unusual activity` is a low risk score on the generate request. Google exposes no score, so the trigger can't be pinned to one factor. Known contributors: `HeadlessChrome` UA (proven, 2/2), **no WebGL** (`--disable-gpu`, which this NAS requires, since SwiftShader and in-process-GPU both wedge the renderer), robotic input (teleport clicks + `insertText`), **many Flow tabs on one account**, and daily volume. Once tripped it stayed tripped for ≥25 min in the same session. Failed cards are not charged (Google Help). Credits were not the cause (432 left).
- **Tab buildup: close Chrome with CDP `Browser.close`, never `pkill`.** `pkill` leaves `Preferences → profile.exit_type: Crashed`, so the next launch restores every tab. The profile had piled up **47 tabs (30 of them Flow, each running reCAPTCHA + polling)** across runs, and the Kathy run submitted with all of them open. After `Browser.close`, exit_type is `Normal` and the relaunch opens with only 2 tabs. Use `pkill` only when CDP is dead. At launch, check `curl :9222/json/list` and close every extra page (`/json/close/<id>`) before working — but only AFTER the working tab has finished loading: pruning within the first seconds of a launch coincided twice with Chrome exiting silently (CDP gone on the very next call, no fatal line in the log), while a launch left unpruned ran a whole clip session cleanly. Re-probe `:9222` after any prune batch; if the port died, relaunch (Singleton cleanup above) instead of debugging the page. **Never close the LAST page target: headful Chrome exits when its final window closes, so CDP dies with it and a mid-pipeline run reads as a silent crash.** Keep one tab alive and navigate it (`new_tab(<project url>)` / `Page.navigate`) rather than closing it, prune only the extras, and if it is already gone relaunch with the project URL as the launch target (fresh log + Singleton cleanup) instead of debugging the page.
- **Pacing rule (Fix chose it 2026-11-09):** keep the 4-6 shot board, and start each submit **≥5 min after the previous one**. Do not cut the board to 2×10 s to save requests, because Fix picked quality over speed. Fill the gap with frame checks, review sends and post work.
- **Count a failure only from the submit you just made.** An older Failed card can stay at the top of the grid, so searching the page text for `unusual activity` after a new submit cannot tell the two apart. Compare the top tile with the prompt you just sent (first words or created time) before calling the submit failed or ok.
- **Drive every control with real mouse events FIRST (`click_at_xy` at a fresh rect).** JS `.click()` and other synthetic events are the robotic input the risk score reads, so real mouse is the first attempt for the picker, `Add to prompt` and `Start generation`. **But a real click can no-op even when the hit-test passes** — `elementFromPoint` returns the button, the click fires, and nothing changes: the settings panel stays closed, the `Download media` menu never opens, `Add to prompt` leaves the chip count at 0, `Start generation` leaves the prompt at full length. Do not fire it a third time: re-read the state to confirm it really is unchanged (prompt still full, chip count still 0, no `[role=menu]`), then one `js('…element.click()')` is the fallback that has opened the settings panel, the download menu and `Add to prompt`, and has submitted a shot with no `unusual activity` card. Judge every click by the state change the control must produce (panel text / `[role=menu]` present / chip count / prompt length back to 1), never by the click's return value — and never after a state change that suggests the real click DID land, or you double-submit.
- **The card is intermittent, not permanent.** Failed cards came back on several submits in a row within a session, then a submit about an hour after a clean relaunch (Browser.close, relaunch on the same profile, no submits in between) rendered normally and did not recur on the next check. Cause still unconfirmed, so the rule is: after a failed submit, stop and report, and retry only after a long gap (≈1 h) with a relaunch. Do not retry in a loop; each retry inside the window deepens the block.
- Do not try to fool reCAPTCHA (fake fingerprints, simulated mouse paths). That is circumventing Google's abuse check and puts the account at risk. Stick to hygiene and pacing.

## Download — try the fast path, then fall back without guilt

- **The editor does NOT always mount that `<video>`** — it can stay absent for a whole render (`querySelectorAll('video')` empty, no element created after repeated waits). That is a lazy-mount quirk, not a broken clip: **stop waiting and fall back to the `Download media` menu in step 7**, which needs no `<video>` element at all.
- **The menu can absorb the click and deliver nothing** — the app shows `Your video has been downloaded!` while no file lands in either Downloads dir. Verify at the SOURCE, not by clicking again: copy `Default/History{,-wal,-shm}` out of the profile to a scratch dir (the live DB is locked by Chrome) and read the `downloads` table — **no new row means the request never reached the browser**, and re-clicking the menu will fail identically (hit-test the item first so a missed click is ruled out).
- **Cheapest rung — the page's own performance timeline already holds the signed URL (no hooks, no payload capture).** With the finished tile's `/edit/<id>` open, `performance.getEntriesByType('resource').map(e=>e.name).find(n=>n.startsWith('https://flow-content.google/video/'))` returns the full signed URL the page requested for that clip — it works when no `<video>` is mounted, when the `Download media` menu will not open, and when the menu-item clicks deliver nothing, because it records the request regardless of which UI path produced it. Egress it with `return btoa(unescape(encodeURIComponent(u)))`, decode in Python, write it to a file, `curl -sL` it from `terminal`, then `ffprobe`: the duration is the verdict (an entry read while `Total duration` still reads `00:00:00` may be stale, so re-read the timeline after the editor reports the real length).
- **Third rung — capture the signed URL the app was going to download.** In the editor tab, before clicking the menu item, install recording hooks that append to `window.__cap`: wrap `window.fetch`, `XMLHttpRequest.prototype.open`, `URL.createObjectURL`, the `HTMLMediaElement.src` setter, and `document.createElement` for tags returning an `<a>` whose `click` records `el.href`. One click on the `720p` item then yields `https://flow-content.google/video/<uuid>?Expires=…&KeyName=labs-flow-prod-cdn-key&Signature=…` in `__cap` (its `blob:` entry tells you the app built a blob from that fetch) — that signed URL is directly fetchable from Python with no cookies and is the file itself. Save it, then run the same `sha256sum` + `ffprobe` gate as any download. Hooks are page state: they survive until the next reload, so re-install them after any reload and clear `__cap` between attempts.
- Either way finish with `sha256sum` (must differ from every existing clip in the folder) + `ffprobe` (720x1280, aac) before sending.
- **Fourth rung — the signed URL is already in the media-list payload, click or no click.** The reload-time `batchexecute` capture (→ Desktop: Decisive check) holds EVERY item's `flow-content.google/video/<id>?…&Signature=…`, so when the menu click, focus+Enter and even click-time recording hooks all produce nothing — no file, no Chrome History row, `__cap` empty — grep that capture for the shot's video id INSIDE `js()` (fold the JSON `\uXXXX` escapes there), `return btoa(url)`, decode in Python, write it to a file and `curl` from `terminal`. The URL exists from payload time, which is why click-time hooks can come back empty; a hit-tested menu click that leaves no History row twice = stop clicking and come straight here.
- **The editor URL only resolves WITH its project segment** — `https://flow.google.com/edit/<id>` serves a bare `Error: 404` page, while `https://flow.google.com/project/<pid>/edit/<id>` loads. Never rebuild the URL from an id you recalled: reuse `page_info().url` as-is (the tile opener already navigated to the full form), or concatenate the project id opened in step 0.
- **A rendered clip reads `Total duration: 00:10:00` in the editor's own body text even when NO `<video>` element is mounted** — that string is DOM text, not video-element metadata, so it survives the lazy-mount quirk. **The SAME editor reads `Total duration: 00:00:00` while the render is still running and flips to the real length when it finishes**, so gate on the VALUE being non-zero (ideally your configured seconds), never on the label's presence — the label is there during rendering too, and a `00:00:00` reading means "not finished yet", not "broken clip". The label and its value sit on SEPARATE DOM lines (`Total duration:\n00:10:00`), so match with `\s*` or read the following line — a space-only regex returns nothing and misreads a finished clip as one that never rendered. Together with the tile's `img[alt="Generated video thumbnail"]` poster it is the cheapest finished-render verdict: it costs no menu interaction, so read it while deciding whether to go straight to the 720p menu instead of polling for a `<video>`. **But that label is not always rendered: the narrow layout draws NO `Total duration` string at all while a `<video>` is already mounted whose `currentSrc` is a signed `flow-content.google/video/<uuid>` URL — and that URL served the finished file straight down, complete. So treat a mounted `<video>` with a signed CDN `currentSrc` as a finished-render CANDIDATE in its own right: curl it and let ffprobe's duration settle the question, rather than polling for a label this layout never draws.**
