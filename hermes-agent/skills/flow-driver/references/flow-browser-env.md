- **CDP is usually DOWN when a session starts** — `browser_exec` fails with `BU_CDP_URL … unreachable`. Cold-start it with the `browser-automation` §1 recipe pointed at this profile: `Xvfb :99` (background) then `DISPLAY=:99 /opt/data/tools/chromium-1208/chrome-linux64/chrome --no-sandbox --disable-gpu --disable-dev-shm-usage --window-size=1280,900 --remote-debugging-port=9222 --user-data-dir=/opt/data/browser-profiles/chrome-flow --no-first-run https://flow.google.com/` (headful on Xvfb, NOT `--headless`; see the `unusual activity` section), started via `terminal(background=true)` (`nohup`/`disown` wrappers are rejected by the tool). Ready = `curl -s http://127.0.0.1:9222/json/version` prints `Browser`. **`--no-sandbox` is mandatory here** — without it Chrome aborts with a sandbox FATAL before CDP ever opens, which looks like a broken launch rather than a missing flag. **`--disable-gpu` (and `--disable-dev-shm-usage`) is ALSO mandatory (learned 2026-10-22): without it the launch comes up with browser-level CDP fully answering while EVERY tab's renderer is wedged.** `Target.getTargets`, `Target.attachToTarget` and `Page.reload` all reply fine, but every `Runtime.evaluate` times out at 5 s — on every tab including a freshly created one — so it misreads as 'the Flow SPA is slow to boot' when it is a dead renderer. Log signature: `ContextResult::kTransientFailure: Failed to send GpuControl.CreateCommandBuffer` plus `vkCreateInstance: Found no drivers`. Diagnostic rule: browser-level CDP alive + all renderers dead = missing `--disable-gpu`, NOT a slow page — stop waiting out the timeouts and relaunch with the flag. `--headless=new` renders the DOM, but its `HeadlessChrome` UA gets every submit rejected (see the `unusual activity` section), so launch headful. Without `--window-size` **the viewport width is not stable across launches**: it has come up at ~800 px (narrow picker) and ~1700 px (desktop picker). `--window-size=1280,900` gives the desktop popover layout. Always read `page_info().w` and branch; never carry selectors over from the previous session. See Layout detection below and `references/flow-picker-dom.md`.
- **Lifecycle — Fix's standing instruction: close Chrome once the clip is delivered** ("งานหน้าจะได้ไม่ต้อง kill เปิดใหม่ทุกรอบ"). Do it as the LAST act of a finished pipeline, never mid-run: killing Chrome between attaching and submitting throws away the ingredient chips, which are page state, so an interrupted session should leave Chrome running and say so, letting the next session resume with `page_info()` and reuse the browser as-is instead of relaunching. Close it with CDP `Browser.close` (see the `unusual activity` section for why pkill is the wrong close).
- Drive via browser_exec: js(), cdp(), click_at_xy(), capture_screenshot()+vision_analyze for DOM-blind states. A browser_exec session attaches to `about:blank` on its first call, so `page_info()` and `js()` read the blank tab until you run `new_tab(<project url>)` (plus `wait_for_load()`); do that before any DOM query.
- **A browser_exec call is cut at ~420 s wall clock regardless of `timeout_s`** (a 1500 s poll loop died at 420 s). Keep each poll loop under ~360 s and call again; a cut loses Python state but Chrome and the chips survive, so re-run the state probe before assuming anything.
- **A stale `SingletonLock` naming a DEAD pid blocks the launch outright**: Chrome exits with `The profile appears to be in use by another Chromium process (<pid>) on another computer` and CDP never opens, while `ps -o pid,args -p <pid>` returns only a header (pid gone). Fix: delete `/opt/data/browser-profiles/chrome-flow/Singleton{Lock,Socket,Cookie}` and relaunch — do not chase the "other process" the message names. Same for `pgrep` hits on the launch pattern that are really the terminal wrapper's own argv: prove liveness with `ps`, never pgrep (see step 12).
- **Give every launch its own log path, spawn Chrome DETACHED from the tool call, and probe `curl -s http://127.0.0.1:9222/json/version` before attaching.** Reusing the previous run's log makes a dead launch indistinguishable from a live one (it still shows the OLD run's output while the port answers nothing), and a Chrome started under a tracked background shell has vanished mid-pipeline with no fatal line in its log — the first symptom is `page_info()`/`Runtime.evaluate` failing on a browser that answered a minute earlier, so re-probe the port before blaming the page. Detached launch that survives the call (shell `nohup`/`setsid`/`disown` wrappers are rejected by the terminal tool): one foreground `execute_code`/`terminal` call running `python3 -c "import subprocess,os; subprocess.Popen(['<chrome>','--no-sandbox','--disable-gpu','--disable-dev-shm-usage','--window-size=1280,900','--remote-debugging-port=9222','--user-data-dir=/opt/data/browser-profiles/chrome-flow','--no-first-run','https://flow.google.com/'], stdout=open('/opt/data/cache/scratch/<fresh-name>.log','w'), stderr=subprocess.STDOUT, stdin=subprocess.DEVNULL, start_new_session=True, env={**os.environ,'DISPLAY':':99'})"` — `start_new_session=True` is what detaches it — then readiness-check in a separate call.
- Prompt editor = div.ProseMirror (may lack data-placeholder): **focus it before typing** — `p.focus()` + select its contents + `execCommand('delete')` to clear, then `cdp('Input.insertText', text=...)` **in ~700-char chunks split on newline boundaries** (`chunk.rfind('\n')`), reading `innerText.length` against `len(PROMPT)` plus a head/tail slice after every pass. An insert into an UNFOCUSED editor lands only its first line (93 of 1,979 chars) while reporting ok, and an insert whose caret sits at position 0 splices the new text BEFORE what is already there — both read as a working prompt unless you check length AND head/tail. ~1,600 chars in one call is not a guarantee; chunking is. **`cdp(...)` is a Python helper inside `browser_exec`, NOT a JS function** — writing it inside `js("cdp('Input.insertText', …)")` dies with `ReferenceError: cdp is not defined` before any text is typed, which reads like a broken editor. Call it from Python; keep `js()` for DOM reads and dispatches.
- **Typing the prompt: ONE full-length `cdp('Input.insertText', text=PROMPT)` beat chunking outright (2026-10-28).** The ~700-char chunk loop reported healthy lengths after each pass (636 → 665 → 674 → 499) while each new insert was REPLACING the whole document instead of appending — the final text was the last chunk only, ~494 of 2,443 chars, and the read-back length per chunk is what caught it. Clearing to an empty editor first, then a single insert, produced innerText whose whitespace-normalised form compared EQUAL to the source file (2,435 = 2,435) on the first try — so try the single insert, verify with `re.sub(r'\s+',' ',text)` equality against the file, and only fall back to chunking if that comparison shows truncation (then re-place the caret at the end before each pass and abort the moment a length shrinks). **Never compare raw `innerText.length` between two reads — it drifts by a few dozen chars as trailing newlines collapse, so a raw mismatch against the file on a normalised-equal prompt is not truncation; the normalised comparison is the only verdict.**
- **`selectNodeContents(pm)` + `execCommand('delete')` wipes the ingredient CHIPS too, not just the text.** Chips live inside the same prompt box, so a clear-then-retype cycle silently drops them: the box read `chips: 0` after typing even though two chips had just been attached. Order that avoids redoing work: type the prompt FIRST, then attach image + character, then submit. The rule behind that order is that a CLEAR is the only forbidden move — attaching first and then inserting into an ALREADY-EMPTY editor keeps every chip too (no second attach cycle), fine as long as you read `chips` back after the insert to prove nothing was dropped — and if a clear is unavoidable, verify `chips` afterwards and re-attach (no re-upload needed) before hitting Start generation. A pre-submit check of `chips == expected` and normalised-text equality is cheap and catches both failure modes at once.
- **`js()` must return plain values** (strings, numbers, arrays, objects of primitives). Returning a DOM element from the expression fails with `Object reference chain is too long`; return `.innerText.length`, a `{x,y}` rect or the `aria-label` string instead.
- Inside `browser_exec` you get plain stdlib Python only: `hermes_tools` is NOT importable there (different interpreter), so read prompt/asset text with `open(path).read()`, not `hermes_tools.read_file`

## `unusual activity` Failed cards — headless UA, then submit bursts
- **`--headless=new` sends `User-Agent: HeadlessChrome/…`.** Check it with `curl -s :9222/json/version`. With that UA every submit dies on a `Failed` card reading *"We noticed some unusual activity. Browser extensions that modify the page may cause issues"*, even though the Google account is in good standing. The fix is to relaunch **headful on Xvfb** (recipe in Environment). The UA then reads plain `Chrome/…` and submits render. Check the UA before the first submit of every run, because one Failed card costs a full chip-attach cycle.
- **Kill Chrome in a terminal call of its own.** `pkill -f '[c]hrome-flow'` also kills the tool's own shell when that same command line contains the literal path (`rm …/chrome-flow/Singleton*`), because `-f` matches the shell's argv. The call then dies with SIGTERM. Run the pkill alone, then do the lock cleanup in the next call (`cd /opt/data/browser-profiles && rm -f chrome-fl*/Singleton*`).
- At 1280 px the project loads in **agent-panel layout**. Close the panel (✕ top right), then use the bottom `flow-prompt-box`. Known contributors: `HeadlessChrome` UA (proven, 2/2), **no WebGL** (`--disable-gpu`, which this NAS requires, since SwiftShader and in-process-GPU both wedge the renderer), robotic input (teleport clicks + `insertText`), **many Flow tabs on one account**, and daily volume. Once tripped it stayed tripped for ≥25 min in the same session. Failed cards are not charged (Google Help). Credits were not the cause (432 left).
- **Tab buildup: close Chrome with CDP `Browser.close`, never `pkill`.** `pkill` leaves `Preferences → profile.exit_type: Crashed`, so the next launch restores every tab. The profile had piled up **47 tabs (30 of them Flow, each running reCAPTCHA + polling)** across runs, and the Kathy run submitted with all of them open. After `Browser.close`, exit_type is `Normal` and the relaunch opens with only 2 tabs. Use `pkill` only when CDP is dead. At launch, check `curl :9222/json/list` and close every extra page (`/json/close/<id>`) before working.
- **Pacing rule (Fix chose it 2026-11-09):** keep the 4-6 shot board, and start each submit **≥5 min after the previous one**. Do not cut the board to 2×10 s to save requests, because Fix picked quality over speed. Fill the gap with frame checks, review sends and post work.
- **Count a failure only from the submit you just made.** An older Failed card can stay at the top of the grid, so searching the page text for `unusual activity` after a new submit cannot tell the two apart. Compare the top tile with the prompt you just sent (first words or created time) before calling the submit failed or ok.
- **Drive every control with real mouse events (`click_at_xy` at a fresh rect).** JS `.click()` and other synthetic events are the robotic input the risk score reads, so do not use them for the picker, `Add to prompt` or `Start generation`.
- **The card is intermittent, not permanent.** Failed cards came back on several submits in a row within a session, then a submit about an hour after a clean relaunch (Browser.close, relaunch on the same profile, no submits in between) rendered normally and did not recur on the next check. Cause still unconfirmed, so the rule is: after a failed submit, stop and report, and retry only after a long gap (≈1 h) with a relaunch. Do not retry in a loop; each retry inside the window deepens the block.
- Do not try to fool reCAPTCHA (fake fingerprints, simulated mouse paths). That is circumventing Google's abuse check and puts the account at risk. Stick to hygiene and pacing.

## Manual hand-off when Flow keeps rejecting a submit
- When a shot fails its one retry (or the same session fails again after a relaunch), stop submitting and give Fix the exact prompt in a code block, the reference image as a `MEDIA:` line, and the settings to match (9:16, 720p, the shot's seconds, x1, which chips to attach, whether a character is needed). He generates in his own Flow session and sends the mp4 back.
- Treat his mp4 as a normal download: `sha256sum` against the folder, then `ffprobe` (720x1280, h264, aac), then the frame check, then the review gate. Record the shot as `manual` in the state file so the next run does not count it as an automated render.
- Do not present the hand-off as the default route. It exists so a blocked session does not stall the whole clip.

## Login after a cookie or session reset (browser_vault)
- **Keep one login tab.** `browser_vault` fills the first tab that matches the saved origin. A stale `accounts.google.com` identifier page left open next to the password page made `fill` fail with `No fillable login field matched`, even though the password field was visible. Close the stale tabs first (`/json/list` → `/json/close/<id>`; `Target.closeTarget` may report a missing target for a tab that is still listed), then call `fill` once.
- Flow: fill the email into `#identifierId` with `fill_input`, press Next, then `browser_vault` `fill` on the password page (a saved login with `identifier` as the email). Never type the password yourself.
- 2-step verification on this account is a tap on the phone ("Check your device"), with no code field, so the run waits for the owner to approve. Poll `/json/list` every ~15 s for the redirect to `flow.google.com` and do not assume it passed until the project page loads.
- **Clearing site data:** `Storage.clearDataForOrigin` returned an internal error and `Network.clearBrowserCache` timed out in this environment. The reliable method is `Network.getAllCookies`, then `Network.deleteCookies` for each cookie whose domain contains `google.com`, `flow.google`, `accounts.google`, `googleusercontent` or `gstatic`. Verify with a second `getAllCookies` (expect zero).
- **Relaunching on the same profile keeps the Google session.** After the cookie clear and a clean `Browser.close`, the relaunch still opened the project logged in, so a full re-login was not needed in that run. Still check `Sign in` text on the page before submitting.

## Layout detection — do this first, every session
`page_info().w` decides which DOM you get and it is NOT stable across launches (~800 = narrow, ~1700 = desktop). Branch on it before touching any picker or prompt-bar control. **Read `.h` in the same breath:** the narrow launch comes up ~800×457, so any control, list row or grid-tile point whose centre sits below `innerHeight` hit-tests to `null` and `click_at_xy` on it is a silent no-op — "inside the viewport" must be true on BOTH axes (full rule in `references/flow-picker-dom.md` → Opening it, and in Pitfalls for tile opening).
- **Scope every prompt-box query to the LIVE editor — the `div.ProseMirror` whose `getBoundingClientRect().width > 0.** At ~1700 px there are two decoys: a preview panel (a second `.base-prompt-box` with NO `ProseMirror`, rendering its own chips and its own `Add ingredients…` / `Start generation` copies), and a hidden duplicate inside `.agent-panel-prompt-box` / `.agent-panel-prompt-box-hidd` that is `display:none` yet still CONTAINS a `div.ProseMirror` at rect 0×0. The old `find(b => b.querySelector('div.ProseMirror'))` and a bare `document.querySelector('div.ProseMirror')` both land on that hidden one, where `cdp('Input.insertText')` reports ok and inserts NOTHING — so always read `pm.innerText.length` back after typing. Resolve by rect instead: `[...document.querySelectorAll('div.ProseMirror')].find(p => p.getBoundingClientRect().width > 0)`, and reach it through `document.querySelector('flow-prompt-box')` when that exists — the real editor is the bottom-centre `FLOW-PROMPT-BOX`, not the right-hand agent panel. Query the picker trigger / `Start generation` / chips through that same ancestor. The hidden panel toggles `display` as the Agent settings drawer opens and closes, so re-resolve it after any drawer or panel interaction.
- **Chip counts are only meaningful inside that box.** Older session cards in the media grid render their own `.chip-container` elements, so a global query returns 20+ chips and reads as "stale chips need clearing" when the live box holds one. Count within the resolved box only.
- **`flow-prompt-box` is not always in the DOM** — after an agent reply or a reload the live editor can sit under `.agent-panel-prompt-box` → `FLOW-AGENT-PANEL` instead, so `document.querySelector('flow-prompt-box')` returns null and a box-scoped query reports "no box" while the editor plainly has chips. Resolve the box by walking UP from the live ProseMirror and stopping at the nearest PROMPT-BOX-LEVEL ancestor — `flow-base-prompt-box` / `DIV.base-prompt-box` / `flow-prompt-box` — NOT at the first ancestor that happens to contain chips: in the agent-panel layout that first match is `FLOW-AGENT-PANEL`, which holds 20–30 chips from historical session cards, so a "walk until chips>0" loop returns the whole panel and reads as "30 stale chips to clear" when the live box holds zero. **Sanity ceiling: in-box chips are 0–3; 20+ means your scope is the panel or the media grid, not the box.** Use the prompt-box-level element for every chip count, chip clear and scope check.
- **To clear a chip genuinely left in the box** (from an earlier clip, or attached by mistake): find the `.hover-icon-overlay mat-icon` with text `cancel` inside the live box, then send real mouse events through CDP at its centre — `cdp('Input.dispatchMouseEvent', type='mousePressed', x=x, y=y, button='left', clickCount=1)` then `mouseReleased`. That removed a wrong chip in the narrow layout (2026-11-08). Re-read the in-box chip count and the prompt length after each removal, since a clear that touches the editor can drop the text too.

## Download — try the fast path, then fall back without guilt
- **Verified 2026-11-09 (MALI BABY run, narrow layout):** mouse clicks on the `720p` menuitem (via the editor's More options, and via the grid tile's Download button) fired NO download — no blob, no anchor, no Chrome History row, even with `Browser.setDownloadBehavior` set. What worked: open the menu, `it.focus()` on the `720p` `[role=menuitem]`, then `Input.dispatchKeyEvent` keyDown/keyUp `Enter`. The file landed in `/opt/data/Downloads/` within ~20 s.
- **Returning the `<video>` `currentSrc` to the tool is blocked by browser_exec** ("Blocked: URL targets a private or internal address") whenever the signed `flow-content.google` URL appears in the output. Use the keyboard download path above instead of spending turns on it.
Open the finished tile (elementFromPoint on its `img.thumbnail`, then pointerdown/mousedown/pointerup/mouseup/click + dblclick) to land on `/edit/<new-id>`.
- **Fast path, when it works:** the editor mounts a `<video>` whose `currentSrc` is a directly fetchable signed URL `https://flow-content.google/video/<uuid>?Expires=...&KeyName=labs-flow-prod-cdn-key&Signature=...` — `curl -sL` it straight into `/opt/data/home/Downloads/`. No menu, no wait; confirmed output 720x1280 h264+aac. **Read that URL out of the DOM IN FULL — never `.slice()` it to keep the printout short: a truncated `Signature` still "downloads" ~100 bytes of XML error body into Downloads that looks like a finished file, so let verify-clip.py's ffprobe/size gate judge it, never its existence.** **Do not wait on the element's readiness** — it commonly sits at `readyState: 0` with `videoWidth/videoHeight: 0` (metadata never loaded) while that signed URL still downloads the full file, so a "not loaded yet" reading is no reason to poll or to fall back to the menu.
- **The editor does NOT always mount that `<video>`** — it can stay absent for a whole render (`querySelectorAll('video')` empty, no element created after repeated waits). That is a lazy-mount quirk, not a broken clip: **stop waiting and fall back to the `Download media` menu in step 7**, which needs no `<video>` element at all.
- **The menu can absorb the click and deliver nothing** — the app shows `Your video has been downloaded!` while no file lands in either Downloads dir. Verify at the SOURCE, not by clicking again: copy `Default/History{,-wal,-shm}` out of the profile to a scratch dir (the live DB is locked by Chrome) and read the `downloads` table — **no new row means the request never reached the browser**, and re-clicking the menu will fail identically (hit-test the item first so a missed click is ruled out).
- **Third rung — capture the signed URL the app was going to download.** In the editor tab, before clicking the menu item, install recording hooks that append to `window.__cap`: wrap `window.fetch`, `XMLHttpRequest.prototype.open`, `URL.createObjectURL`, the `HTMLMediaElement.src` setter, and `document.createElement` for tags returning an `<a>` whose `click` records `el.href`. One click on the `720p` item then yields `https://flow-content.google/video/<uuid>?Expires=…&KeyName=labs-flow-prod-cdn-key&Signature=…` in `__cap` (its `blob:` entry tells you the app built a blob from that fetch) — that signed URL is directly fetchable from Python with no cookies and is the file itself. Save it, then run the same `sha256sum` + `ffprobe` gate as any download. Hooks are page state: they survive until the next reload, so re-install them after any reload and clear `__cap` between attempts.
- Either way finish with `sha256sum` (must differ from every existing clip in the folder) + `ffprobe` (720x1280, aac) before sending.
- **The editor URL only resolves WITH its project segment** — `https://flow.google.com/edit/<id>` serves a bare `Error: 404` page, while `https://flow.google.com/project/<pid>/edit/<id>` loads. Never rebuild the URL from an id you recalled: reuse `page_info().url` as-is (the tile opener already navigated to the full form), or concatenate the project id opened in step 0.
- **A rendered clip reads `Total duration: 00:10:00` in the editor's own body text even when NO `<video>` element is mounted** — that string is DOM text, not video-element metadata, so it survives the lazy-mount quirk. **The SAME editor reads `Total duration: 00:00:00` while the render is still running and flips to the real length when it finishes**, so gate on the VALUE being non-zero (ideally your configured seconds), never on the label's presence — the label is there during rendering too, and a `00:00:00` reading means "not finished yet", not "broken clip". The label and its value sit on SEPARATE DOM lines (`Total duration:\n00:10:00`), so match with `\s*` or read the following line — a space-only regex returns nothing and misreads a finished clip as one that never rendered. Together with the tile's `img[alt="Generated video thumbnail"]` poster it is the cheapest finished-render verdict: it costs no menu interaction, so read it while deciding whether to go straight to the 720p menu instead of polling for a `<video>`. **But that label is not always rendered: the narrow layout draws NO `Total duration` string at all while a `<video>` is already mounted whose `currentSrc` is a signed `flow-content.google/video/<uuid>` URL — and that URL served the finished file straight down, complete. So treat a mounted `<video>` with a signed CDN `currentSrc` as a finished-render CANDIDATE in its own right: curl it and let ffprobe's duration settle the question, rather than polling for a label this layout never draws.**
