# Flow ingredient-picker DOM map (step 3 only)

Selectors and verification signals for the asset picker. All confirmed against the live app; use these instead of re-probing the DOM from scratch.

## Opening it
- **The live prompt box is the `div.ProseMirror` whose `getBoundingClientRect().width > 0`, reached through `document.querySelector('flow-prompt-box')` when that exists — the real editor is the bottom-centre `FLOW-PROMPT-BOX`, not the right-hand agent panel.** Two decoys sit at ~1700 px: a preview panel (a second `.base-prompt-box` with no `ProseMirror`, rendering its own chips and button copies) and a hidden duplicate inside `.agent-panel-prompt-box` / `.agent-panel-prompt-box-hidd` that is `display:none` yet still CONTAINS a `div.ProseMirror` at rect 0×0 — `cdp('Input.insertText')` into that one returns ok and inserts nothing, so always read `pm.innerText.length` back after typing. `find(b => b.querySelector('div.ProseMirror'))` and a bare `document.querySelector('div.ProseMirror')` both land on the hidden copy. The hidden panel toggles `display` as the Agent settings drawer opens/closes, so re-resolve after any drawer interaction. Query the picker trigger / `Start generation` / chips through the live ancestor; a global query reads state that is not the live one.
- **Chip counts are only meaningful inside the prompt-box element.** Older session cards in the grid render their own `.chip-container`, so a global `document.querySelectorAll('.chip-container')` returns 20+ and reads as "stale chips to clean" when the live box holds one. Scope to `FLOW-BASE-PROMPT-BOX` (`document.querySelector('flow-base-prompt-box')`) — that custom element wraps the live editor in the agent-panel layout where `flow-prompt-box` is absent — and count `.chip-container` within it. **Do NOT resolve the box by walking up to the first ancestor that contains chips:** in the agent-panel layout that ancestor is `FLOW-AGENT-PANEL`, which holds the whole session history (20–30 chips). Sanity ceiling: a real in-box count is 0–3; anything higher means you are scoping to the panel or grid.
- **To clear a chip left in the live box** by an earlier clip: dispatch the pointer/mouse sequence on that chip's `.hover-icon-overlay mat-icon` (text `cancel`, a child of its `.chip-container` button), then read the in-box chip count back.
- Trigger: `button[aria-label="Add ingredients to the prompt box"]`. **Query by aria-label globally** — do NOT scope to `.agent-panel-prompt-box`; that wrapper class is absent in the narrow-viewport layout, so a scoped query returns `no-btn` for a button that is plainly in the DOM and dispatchable. (Globally means "across the document", then filter by the live-box rule above — not "take the first match").
- Its siblings in the same bar: `[aria-label="Agent instructions"]`, `[aria-label="Settings"]`, `[aria-label="Start generation"]`.
- The bar hugs the right edge, so these buttons sit at `x ≈ innerWidth-8 .. innerWidth+24` — their center is frequently OUTSIDE the viewport (see the SKILL.md pitfall on off-viewport controls).
- **Real `click_at_xy` beats synthetic dispatch for everything INSIDE the picker; synthetic dispatch is only for the prompt-bar buttons.** Picker controls live at `x ≈ 170–1180`, well inside the viewport, so the working click is: take the control's rect, hit-test `document.elementFromPoint(cx,cy)` (accepting the card's own `.asset-title` span or a `mat-list-item` descendant — require `closest('button.asset-item')` / `closest('mat-list-item')` to be truthy), then ONE `click_at_xy(cx,cy)`. A pointer sequence dispatched via JS on a `button.asset-item` or a category `mat-list-item` reports ok and attaches NOTHING (chip count flat, card still listed): synthetic mouse events are not trusted by these Angular list options. Only the prompt-bar buttons, whose centres sit at `x ≥ innerWidth` and cannot be hit-tested at all, need the JS pointerdown→mousedown→pointerup→mouseup→click sequence on the element.
- **VERTICALLY the method changes, the verdict does not: compare the row's centre y against `innerHeight` before choosing how to click it.** The narrow layout's viewport is only ~457 px tall while the picker list and a 9:16 grid tile both run past it (a list row at y ≈ 480, a tile img to y ≈ 604), so a centre below `innerHeight` hit-tests to `null` and `click_at_xy` there is a SILENT no-op — it reads as 'the card did nothing' or 'the card would not attach'. For such rows SCROLL THE CARD INTO THE VIEWPORT FIRST (`card.scrollIntoView({block:'center'})` inside the same js() call that locates it), re-read its rect, hit-test again, then ONE `click_at_xy`: that attached first try on a character card where dispatching the pointer sequence on the still-off-viewport element returned `dispatched` and attached NOTHING (chip count flat, no `Add to prompt`). The pointer sequence on the element stays as the LAST resort when the scroll cannot bring the row inside — it has attached in other rounds, so it is a coin flip, never the primary method. So the decision is two-axis: inside the viewport on both axes → real `click_at_xy` after a hit-test; centre off the RIGHT edge (prompt-bar controls) → dispatch on the element; centre below the BOTTOM edge (picker row) → scroll it up, then a real click. Either way the chip count inside the prompt box is the only verdict.

## Picker layout
- **Two layouts exist and which one you get is viewport-dependent, and the width is NOT stable across launches** (~800 px narrow and ~1700 px desktop have both been observed from the same launch command). Read `page_info().w` first, then branch — never assume either `.right-panel` or `.mobile-add-menu-container` exists.
- Desktop/narrow-independent core: `FLOW-ADD-MENU-ASSET-LIST` > `CDK-VIRTUAL-SCROLL-VIEWPORT.asset-list-viewport` (role=listbox, virtual-scrolled — scroll a card into view before reading its rect). This subtree is the same in both layouts; `.right-panel` is not.
- **Desktop layout (~1700 px viewport): the picker is a POPOVER, not `.right-panel`.** Root `FLOW-ADD-MENU-POPOVER-CONTENT` > `DIV.panels-layout` > `FLOW-ADD-MENU-SIDE-NAV`, which holds BOTH the category list and the upload button. `.right-panel` also exists at this width (it is the project's asset browser: `search-header` + `Asset list`) — it is NOT the picker; driving it wastes turns.
- **Desktop picker internals:** category buttons are `mat-list-item` inside `FLOW-ADD-MENU-SIDE-NAV` at `x ≈ 170` (labels exactly `dashboard All`, `image Images`, `videocam Videos`, `voice_selection Voices`, `accessibility_new Characters`, `face Avatars`, `drive_folder_upload Uploads`); `Upload media` is the last button in the same side nav's `.sidebar-footer`, and it often carries NO `aria-label` — find it with `[...nav.querySelectorAll('button')].find(b => b.innerText.includes('Upload media'))`; an aria-label filter returns `no-btn` on a button that is plainly present, which misreads as 'the footer is gone' and sends you hunting a layout that is still on screen. Asset cards then sit at `x ≈ 296`. **Disambiguate by ancestry, not coordinates** — the left project sidebar carries an identically-labelled `Uploads` / `Characters` / `Videos` entry (x ≈ 16–142 depending on layout); require the match to be inside `flow-add-menu-side-nav`. Query category rows ONLY as `.cdk-overlay-container span, .cdk-overlay-container button` — a global `querySelectorAll('span')` matches the sidebar first in DOM order, and clicking that while the picker is open lands on the picker's modal backdrop (`elementFromPoint` returns `cdk-overlay-backdrop`), which CLOSES the picker: overlay innerText drops to ~0 and the round reads as "the category click did nothing". Always hit-test the row's centre before `click_at_xy` and require it to return that row's own SPAN.
- **A single card click may attach IMMEDIATELY in either layout — the split is not by viewport.** At ~1700 px one card showed `asset-item-active` plus an `Add to prompt` button, while the next two attaches (a saved character, and an image right after a tab restart) landed on the click alone: no `asset-item-active`, and a `button` lookup for `Add to prompt` returned `no-el`. So click the card for real (click rule above), then read the chip count inside the live box — if it moved, there is no button to find; only when the count did NOT move should you look for `Add to prompt` (innerText match, e.g. at `x ≈ 550`).
- **Narrow layout (~800 px viewport): container is `FLOW-MOBILE-ADD-MENU` / `.mobile-add-menu-container` over a `.mobile-overlay`, and there are NO category tabs at all.** Categories live behind a single dropdown button in the menu header (shows the current category name + `arrow_drop_down`, `x ≈ 12, y ≈ 76`) which opens a `.filter-panel` (`role=listbox`, `aria-label="Asset categories"`) of `button.filter-option` entries: All / Images / Videos / Voices / Characters / Avatars / Uploads. Select one by hit-testing its centre and ONE `click_at_xy` — both the dropdown and the option rows sit well inside the viewport, so the pointer-dispatch sequence is only the fallback when the hit-test misses. `Upload media` in this layout sits top-right (`x ≈ 752, y ≈ 76`, `w ≈ 36`), and at an 800 px launch its centre (≈770) is still INSIDE the viewport: hit-test first and `click_at_xy` when `elementFromPoint` returns the button or its `mat-icon`; dispatch the pointer sequence on the element only when the hit-test misses (a narrower launch, or a rect in the `innerWidth-8..+24` band like the prompt-bar controls). Coordinates are per-launch — branch on the hit-test, never on the approximate x.
- Picker categories: All / Images / Videos / Voices / Characters / Avatars / Uploads.
- `Upload media` button sits below the list inside the picker (not in the sidebar).

## Asset cards
- Card: `button.asset-item` (role=option) > `FLOW-ADD-MENU-ASSET-ITEM` > `.asset-text`.
- `.asset-text.textContent` CONCATENATES filename + type — e.g. `img_abc.jpgImage`. Match with `startsWith(filename)`, never equality.
- **`asset-item-active` is one possible signal, not the definition of success** — it is absent on direct-attach clicks. Success = the chip count inside the live box went up; secondarily, the card vanishes from the picker list. A click that lands on the `.asset-text` span or the custom-element wrapper (both 0×0 or text-only) does nothing, and a flat chip count is what catches it.

## Verification signals (read back, never assume)
- Card selected (only on a select-then-add path) → `button.asset-item.asset-item-active` exists for that filename; on a direct-attach click it never appears.
- **`Add to prompt` landed → a `.chip-container` with `img[alt="Ingredient image"]` (or `"Character ingredient image"`) appears.** The picker closes and the bar returns to preview state either way, so the picker's disappearance alone proves nothing.
- **A freshly uploaded asset's `Add to prompt` can be `disabled:true` until its thumbnail finishes processing** — the card is selectable and listed, but the detail pane shows no image (`imgs: 0`) and the button refuses the click for ~30–60 s. This is NOT a broken picker and NOT a stale selection: test it by clicking an OLDER asset, whose button enables immediately (`imgs: 1`, `disabled: false`) — that contrast is the diagnostic. Wait it out (re-read the button's `disabled` every ~30 s) instead of reloading (wipes the chips you already attached) or re-uploading (duplicates the file). The same wait applies when a character card is clicked straight after an image attach.
- **A card click may attach with no selection state and no `Add to prompt` button in view** — don't read `sel: [], addBtns: []` as failure: click the card for real, then read the chip count. This wasted probes in both layouts before the chip count was treated as the verdict. **Neither card type may be assumed to attach on click alone** — an image AND a character have both been seen to take EITHER path, in the same picker session, so treat direct-attach vs select-then-`Add to prompt` as a per-click coin flip, never as a property of the asset type: chip count flat → confirm `asset-item-active` names the card you just clicked → press `Add to prompt` if it is `disabled:false`; chip count moved → no button exists to find.
- **Strongest signal: the attached asset VANISHES from the picker's list.** An image that is now a chip no longer appears in the Uploads/Recent list — so if you re-open the picker and cannot find a filename you already attached, that is confirmation, not data loss. Compare against the chip count **inside the prompt-box element** (`flow-base-prompt-box`, see the scoping rule above), never a global `.chip-container` query.
- Upload landed → the new filenames are listed in the picker's Uploads/Recent list (~12 s for a 10-file batch). The list re-sorts with newest first and may carry a stray `image` title prefix above the filename — match with `includes(filename)`, not line equality.
- **Chips carry no filename — identify them by the `<img src>` uuid.** A chip's only visible text is its `cancel` icon, so after any attach cycle read `[...box.querySelectorAll('.chip-container img')].map(i => i.getAttribute('src'))`: each image ingredient resolves to `https://flow-content.google/image/<uuid>?…`. That uuid is the only way to prove WHICH assets are really in the box (a stale-preview attach keeps the count right and the image wrong), and to learn what a uuid points to, fetch its signed URL and look at it — **the CDN re-encodes uploads, so a chip's bytes never sha256-match your local file**: identify by description/vision, never by hash.
- **A chip can be the WRONG asset with the count still right.** A card lookup by name matched a different card than the one named, and two unrelated photos (a person holding a toothpaste tube, another product) were attached while the count read 2 for 1 expected. Verify identity every time, not only the count: fetch each chip's `<img src>` (public `flow-content.google/image/…` URLs fetch fine) and check the JPEG dimensions (`SOF` marker) against the file you staged, or, if the fetch returns an HTML sign-in page (character chips do), capture the chip's rect with `Page.captureScreenshot` (`clip`, `scale: 3`) and vision-read it. Remove a wrong chip by hovering its `.chip-container` and clicking the `cancel` mat-icon centre with `click_at_xy`, then re-check the count is back to 0 before re-attaching.
- **Narrow-layout card targeting:** the `FLOW-ADD-MENU-ASSET-ITEM` custom element reports a 0×0 rect, so click the centre of its inner `img` (or its first child) instead, after `scrollIntoView`. Match the card on its first `innerText` line (`split('\n')[0].trim()`), using `===` for a character name and `startsWith` for a filename.
- **A fresh upload can attach ITSELF as a chip** — the count can rise during `setFileInputFiles` with no `Add to prompt` press. Read the in-box count immediately after the upload settles instead of assuming it starts from zero, so you know whether the file already counts toward the batch and don't add it a second time.

## Multi-select behaviour
- **One click may attach and close the menu, and the next selection into a closed (or preview-state) menu silently misses** — so after EVERY attach, close the picker with CDP Escape (SKILL.md step 3 — a JS `KeyboardEvent` on `document.body` does NOT reach the popover, and clicking outside at x<200 lands on the project sidebar and navigates away) and reopen it (re-clicking the Uploads/Characters category) before picking the next item. On a select-then-add path the pane switches to preview state after `Add to prompt`, which is why a second selection misses the same way.
- **A reopened picker keeps a STALE `asset-item-active` on a previously selected card** — it reopens in the last-used category with an unrelated card (e.g. last clip's upload) still marked active, while the asset you just attached has vanished from the list. So before every `Add to prompt` press, read WHICH card carries `asset-item-active` and require it to be the card you just clicked; pressing the button against a stale selection attaches the previous clip's asset instead, which pollutes the new generation just as a stale chip does.
- `DOM.setFileInputFiles` accepts the WHOLE batch in one call; do not loop per file.
- **Closing the picker via keyboard is safer than clicking around:** dispatch Escape from Python with `cdp('Input.dispatchKeyEvent', type='rawKeyDown', key='Escape', code='Escape', windowsVirtualKeyCode=27, nativeVirtualKeyCode=27)` then the matching `keyUp` (a JS `new KeyboardEvent('keydown')` on `document.body` does NOT reach the overlay). Verify with `.cdk-overlay-container` innerText ≈ 0 chars, or `!!document.querySelector('flow-add-menu-popover-content')` → false before the next open.
- **Batch-attach loop (N images + character):** for each item → open picker → click the target category → real-click the card → read the chip count → Escape-close → next. A `no-el` on the card lookup IMMEDIATELY after uploading means the list has not rendered that file yet, NOT that the upload failed — reopen the picker once and retry that file before ever re-uploading it.

- Open the picker with a real click on the `Add ingredients to the prompt box` trigger (re-read its rect first; it sat at about (359, 700) at 1280 px).
- The upload control is the leaf SPAN whose innerText is exactly `Upload media`, inside the picker's side-nav footer. The project-level `Add media` menu's `Upload` item does NOT open a file input: a DOM query after it returned nodeId 0. Use the picker's span.
- Arm `Page.setInterceptFileChooserDialog`, real-click the span, then take a FRESH `DOM.getDocument(depth=-1, pierce=True)`, `DOM.querySelector` from the root for `input[type=file]`, and `DOM.setFileInputFiles` with all files. At this width it worked first try without the MutationObserver recipe below.

- The picker's search box silently filters the list: typing a filename can show zero rows. Clear it with CDP key events (Ctrl+A, then Backspace) before scanning the list, and do not type into it to find an item you can already see.
- One card per picker open: real-click the card, then read the in-box chip count. If the count did not move, press `Add to prompt` in the preview pane (centre about (818, 535) at 1280 px). Reopen the picker for the next item.

## Narrow-layout character and trigger quirks (confirmed on the 800 px layout)
- **The `Add ingredients to the prompt box` trigger moves between sessions and between prompt states.** Re-read its rect (`getBoundingClientRect`) before every click; a coordinate reused from an earlier attach landed on the wrong control and attached an unintended character chip with no visible confirmation.
- **Read the chip list by `alt` plus `src` before typing any prompt.** The chip alt only says `Ingredient image` or `Character ingredient image`, so the type is visible but the identity is not. Identify a character chip by a screenshot of its thumbnail, and if it is the wrong person, remove it through its `cancel` icon and re-check the count.
- **The narrow picker's character list is a window that changes with scrolling.** Scroll the overlay container (`scrollTop += 500` on every scrollable element inside `.cdk-overlay-container`) and re-read the character names (น้อง…) after each step; the names visible after a scroll are not the same set as before. Choose the character from the names visible at that moment, and never assume a roster name is present because the sidebar lists it.
- **Scroll a character card into view before its click.** `scrollIntoView({block:'center'})` inside the same js() call, then re-read the rect and do one real `click_at_xy`; a card with its centre below `innerHeight` silently ignores the click.

## Stale / incomplete lists
- The category list is virtual-scrolled, so its rendered contents are a WINDOW: an item can be genuinely present yet absent from the DOM. Setting `cdk-virtual-scroll-viewport.scrollTop = 0` scrolls but does NOT refresh a stale list.
- Cross-check the sidebar: the left-hand Characters page lists every saved character. If the picker's Characters category shows fewer (or an empty list) than the sidebar, the list is stale — do NOT conclude the character is missing or create a new one.
- After enough open/attach cycles in one page session the picker can stop opening at all (`button[aria-label="Add ingredients to the prompt box"]` dispatches but no asset-list container appears — `.right-panel` on desktop, `.mobile-add-menu-container` on narrow), and a category tab can fail to load while the picker itself still opens (Characters tab returns an empty list).
- **"The picker stopped opening" has two causes and only one of them is recoverable for free — hit-test before you reload.** `flow-loading-page` can come back MID-SESSION (not just at load) with `opacity:1; pointer-events:auto` covering the whole viewport, so a picker that opened fine two cycles ago suddenly stops opening because its `Loading…` shell swallows the click. Hit-test the trigger: if `elementFromPoint` returns `FLOW-LOADING-PAGE` or another page-level ancestor, run `document.querySelectorAll('flow-loading-page').forEach(e=>e.remove())` and retry — that fix preserves every chip, whereas the reload fallback wipes them and forces a full re-attach. A project-URL reload is the answer ONLY when no overlay is present AND you are ready to redo the whole attach step.
- **A transient `input[type=file]` is easier to keep than to re-find — and it must be kept ALIVE and EVENTED, not just referenced.** It appears only after `Upload media` and is torn down almost immediately. A tag on an already-detached node does not help: `DOM.setFileInputFiles` then returns `{}` while silently doing nothing — and neither the CDP return value nor a readable `input.files.length` is evidence either way (Angular can consume the files and remove the input before you read it), so the verdict is always the filename in the Uploads list.
  - **CONFIRMED WORKING SEQUENCE (2026-10-25, after ~6 failed attempts):** (1) arm a `MutationObserver` on `document.body` BEFORE clicking, storing every new `input[type=file]` into a page variable (`window.__fileInputs`) and tagging `id`; (2) `cdp('Page.setInterceptFileChooserDialog', enabled=True)` first, then real-click `Upload media`; (3) re-append the captured node with `document.body.appendChild(inp)` so `isConnected === true`; (4) resolve the node id as `cdp('Runtime.evaluate', expression="document.getElementById('<id>')", returnByValue=False)` → `cdp('DOM.requestNode', objectId=<objectId>)` → `cdp('DOM.setFileInputFiles', files=[...], nodeId=<nodeId>)` — **`DOM.getDocument` → `DOM.querySelector` on `#id` can return nodeId 0 / "Could not find node with given id" for a node JS just reported `isConnected`**, so skip THAT `#id`-based lookup rather than re-appending or re-uploading; `requestNode` off the live object usually answers — but it too can come back `nodeId: 0` once Angular has torn the input down, which is NOT a dead end: leave interception armed, click `Upload media` once more, then take a FRESH `DOM.getDocument(depth=-1, pierce=True)` and resolve `input[type=file]` from THAT document node (the document-level query, not any `#id` one) before setting the files; (5) **dispatch `new Event('change',{bubbles:true})` on the STORED node reference** — not via `getElementById`, because Angular may have torn it down again between the call and the lookup (`getElementById` returning null right after `setFileInputFiles` is normal and is NOT evidence of failure). Dispatch step 5 whenever the node is still reachable — but Angular may consume the files and REMOVE the input during `setFileInputFiles` itself, so the input can already read `no-input` at dispatch time and a handler answering `{ok:false, reason:'no connected input'}` can still be a landed upload. Never abort on either reply and never treat an unreadable `files.length` as a failed upload: the ONLY verdict is the filename appearing at the top of the picker's Uploads list (~6–12 s after the set call).
  - Why it bites: Angular's file handler listens for `change` on that specific element; `setFileInputFiles` only fills `files` and raises nothing, so a detached-then-refilled input looks primed (`files.length === 1`) while the app sees no event at all.
- **The freshly opened picker defaults to a MIXED list containing uploads AND saved characters together.** Use it: when a category tab is broken or stale, do not switch categories at all — the default list is enough to select both an image and a character. A character card's title is just its name (e.g. น้องมิ้นท์) with an `accessibility_new` icon and type `Character`; select it exactly like an image card — match on `includes(name)`. **But that default list is a newest-first WINDOW too:** a roster character that has not been attached in recent clips is simply not rendered, and its absence there is not evidence it is gone — switch to the Characters category to re-render the full roster first (narrow: header dropdown → `.filter-panel` → the `Characters` `filter-option`, hit-test then one real click; desktop: the side-nav `Characters` row) before scrolling or concluding the character is missing.
- **Reach a known saved character through the picker's Search box when the category switch does not take.** `FLOW-MOBILE-ADD-MENU input[type=text]` (placeholder `Search`) filters the CURRENT list, and the default mixed list already holds saved characters, so typing the character's exact name (e.g. `น้องพีช`) yields its card in one fill + one real click — no dropdown round-trip. The dropdown path fails quietly and reads as "the roster does not contain her": clicking a `button.filter-option` at its `getBoundingClientRect()` top-left instead of its centre closes the panel without switching, and the list you then read is the OLD category. So read the list back for names you expect before trusting a category switch, and fall back to Search rather than re-clicking the option (the centre-click rule stands; this is the recovery when it was missed).
- **`Page.reload` wipes every `.chip-container` in the prompt box** (verified: chip count 0 immediately after reload), even though in-app navigation, category switching and picker close/reopen all preserve them. Uploaded FILES are unaffected and come back in the list, so re-attaching after a reload costs clicks, not re-uploads. Reload for a stuck picker only when you are ready to redo the whole attach step — which is also why step 5's 'ALWAYS reload before checking status' must happen AFTER submission, never between attaching and submitting.
