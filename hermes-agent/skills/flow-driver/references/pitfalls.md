# Flow Shopee clip pitfalls (moved verbatim from SKILL.md 2026-11-05)

Grep this file for the symptom before debugging any failure (Flow DOM, chips, render, download, delivery, audio). Every entry was paid for with a real run.

- **An image message that repeats a file already in the intake folder is a duplicate, not a new input.** Compare its sha256 against the staged `img*.jpg` files first; a match means it is already in the brief, so answer with its slot number and move on. Re-running intake or re-running vision on it spends rounds and changes nothing; only a new hash is new material.
- **A shop ad composite is too small to use as a product reference by itself.** A ~950 px ad image holds the product at ~300 px (below the 1000 px floor in SKILL.md intake rules), and faces sit beside it in the same frame. Ask once for a product-only photo with the reason. If the user chooses the small crop anyway, upscale to 800 px with LANCZOS, record the choice in the state file, and expect Flow to re-draw the packaging rather than copy its details.
- **The narrow-layout settings popover stays open after a choice and swallows clicks on the prompt box.** Close it with CDP `Input.dispatchKeyEvent` keyDown + keyUp Escape, then hit-test the text field before `Input.insertText`: a click under the open panel is silently eaten, and the subsequent insert looks like a failed paste when the field was never focused.
- **Clearing Google cookies on the Flow profile logs it out, and the agent cannot finish the login.** It needs the user's own credentials and a visible browser. Confirm the user is ready to sign in before clearing, and see `references/strategy-and-alternatives.md` for the CDP cookie-delete path.
- **`js()` cannot return a DOM element.** Returning a node reference raises `Object reference chain is too long` and aborts the whole call, which reads like a dead page. Return primitives (`{x, y}`, `innerText.length`, a `slice`) and take the verdict from those.

- **An uploaded asset can VANISH from the picker's Uploads list between submits** — a file that was attachable minutes earlier comes back `No assets found.` on search and is absent from every scroll position, because assets referenced by a submitted generation do not outlive it. The fix is a re-upload of the same local file (~15 s through the `Page.setInterceptFileChooserDialog` recipe), never a hunt: three passes proving "not found" already mean the file is gone, not that your query is wrong, and a `Page.reload` to fix the picker would cost every chip you have attached.
- **Find a known filename through the picker's Search box, not by walking the list.** The list is a `CDK-VIRTUAL-SCROLL-VIEWPORT`, so only the rendered window exists in the DOM and a `scrollTop` sweep can come back empty for an item that is present (or for the wrong category list you forgot you were still on). `FLOW-MOBILE-ADD-MENU input[type=text]` (placeholder `Search`) filters in place: one fill, read the head for `No assets found.` or the card, one click — and an empty search result is then a real verdict instead of a scrolling artefact.
- **Never click a chip or its `cancel` while the ingredient picker is open.** The overlay covers the prompt bar, so `elementFromPoint` at the chip's coordinates returns a picker CARD and the click ATTACHES an asset instead of removing one — the chip count goes *up* when you meant it to go down. Close the picker and confirm `FLOW-MOBILE-ADD-MENU` is absent before any chip add/remove.
- **Judge a chip attach by the INCREASE over a printed baseline.** Print the count before the click, act, print it after, and treat "did not grow" as "not attached" — a click that reports `ok`, a hit-tested card and a present `Add to prompt` button can all be true while the count stays put, and the baseline is the only reading that separates "attached the same number again" from "attached nothing".
- **`hermes send --to telegram:...` can fail with `Platform 'telegram' is not configured … no TELEGRAM_BOT_TOKEN`** — this box now carries a hand-copied `TELEGRAM_BOT_TOKEN=` line in `/opt/data/.env` (mode 600) exactly so `send` works from any session; if that line is missing (fresh volume) or stale (the vault rotated the bot token), `send` cannot see a credential that lives only in the running gateway's process. The `send` CLI reads config/env files, so it cannot see a credential that lives only in a process. Working fix that needs no config change: read the token straight out of the gateway's own environ and call the Bot API with it — find the gateway pid (`hermes gateway status`, or `ps` for `hermes gateway run`), then `TOK=$(tr '\0' '\n' < /proc/<pid>/environ | grep '^TELEGRAM_BOT_TOKEN=' | cut -d= -f2-)`, and send the file via `curl -sS -X POST "https://api.telegram.org/bot${TOK}/sendDocument" -F chat_id=<chat_id> -F document=@<path> -F caption=<text>` (or `/sendMessage` for text), checking the returned JSON `"ok": true`. Confirm delivery by the API's `ok`/`message_id`, not by the absence of an error. Guard the token: capture it into a shell var and never `echo` it into logs or your reply.
- **A clip can ALSO die on media UPLOAD timeout, twice in a row (2026-10-28, FINAL FANTASY run) — skip straight to the Bot API, do not retry the same command.** Two failure signatures, both meaning "the file is fine, the pipe is not": (a) the inline `MEDIA:` line in the reply lands as plain text with no attachment (`No deliverable text or media remained after processing MEDIA tags`), and (b) `hermes send --to telegram:<id> 'MEDIA:<path>'` returns `{"warnings":["Failed to send media <path>: Timed out"]}` — a second identical attempt timed out identically, so never burn a third. Remedy — probe the pipe first, then upload in the BACKGROUND: `TOK=$(grep '^TELEGRAM_BOT_TOKEN=' /opt/data/.env | cut -d= -f2- | tr -d '\r\n')` then `curl -sS --max-time 540 -X POST "https://api.telegram.org/bot${TOK}/sendVideo" -F chat_id=<id> -F video=@<clip>.mp4 -F caption=<one short line> -o <scratch>/tg.json -w 'HTTP %{http_code}\n'` — use `sendVideo`, not `sendDocument`, so the clip plays inline like every other delivery; verify `ok:true` + a `message_id` + `video.file_size` equal to the local byte size in the response, then delete the temp JSON. **Run that curl as a `terminal(background=true)` job and poll the output JSON — a foreground `--max-time 180` on a multi-MB file returns 0 bytes after the full 180 s, which reads like a dead pipe when the pipe is perfectly fine.** The probe is `curl .../sendMessage -F chat_id=<id> -F text=ping` (<1 s): `ok:true` means the token and route are fine, so keep this exact approach and only give the upload more room; a probe failure means the token, not the payload. Resolve the chat id with `hermes send --list telegram` (it prints name → id) instead of guessing. **Run `hermes send` with `--json`, so success comes back as a parseable `message_id`:** on a `MEDIA:` send carrying a multi-line caption the plain output can be the caption text itself, so exit 0 is NOT proof the file landed — the JSON handle is, and it is what you quote when Fix reports a missing clip. Trigger: Fix reporting "ไม่เห็นคลิป" — the agent's own `MEDIA:` line reports NO error when the upload times out, so an attachment-less reply must be re-sent on the spot rather than explained away.
- **`execute_code` is blocked in unattended webhook sessions** (`BLOCKED: … no user present to approve`) even though the same code path would run elsewhere — do the work with `terminal`/`read_file`/`search_files` instead of routing shell work through `execute_code` when the surface is an unattended webhook.
- **Flow REFUSES video generation when a reference image shows a real athlete, celebrity or other prominent person — OR ANY humanoid figure the classifier reads as a person, including rendered/stylized game-character artwork printed on the product itself** (character livery on a controller strap/faceplate triggered it while the pre-submit verification kept answering "no real human face", so the check must ask about humanoid figures, not faces — `product-image-prep` step 5). Surfaced as a chat bubble reading "This prompt might violate our policies about generating prominent people" AND/OR as an explicit `Failed` card; the on-screen note says no credits are lost, and that is true. Rephrasing the prompt to "do not recreate the person" does NOT fix it (three refusals, 2026-10-26, EA SPORTS UFC 6 cover art showing Max Holloway) — the refusal is driven by the ATTACHED IMAGE, not the wording. Remedy that worked: ffmpeg-crop the shop's ad composite down to person-free branding strips (PS5 top banner + title lettering = `crop=W:H:X:Y`; the title-logo strip), vision-verify each crop for even a sliver of a head at an edge (the case's cover art puts a forehead in the crop at 120 px tall; 100 px was clean), attach those instead of the full art, and tell the prompt to keep the case cover turned away from the camera. Prepare the crops while polling so the run can pivot inside the same turn.
- **The same "prominent people" refusal can be triggered by the CHARACTER chip, not the product art (2026-11-01, GameSir X5 Lite for XBOX Fortnite Edition).** Three submits died on that card in a row: (1) Fix's ad crops, (2) ONE clean ad crop, (3) official GameSir renders from the Shopify CDN that had been vision-verified twice as showing NO human/humanoid at all — identical cards every time, `refunded`, so no credits moved. The only element common to all three was the saved character chip (น้องพีช) plus the presenter prompt; the 4th submit dropped the chip, switched to the `hands` preset and passed the policy check on the first try and rendered. **Decision order for a repeat of this card:** vision-check the product art ONCE for humanoids → if it comes back clean, stop re-cropping the art (more crops cost rounds and change nothing) swap the CHARACTER chip for a different saved character next (same product image and prompt — one swap keeps the presenter style and tests the chip itself; a refusal that clears on the swap pins the chip as the trigger); only if the swapped character also refuses, take the chip out and convert the prompt to `hands` (preset in `templates/styles.md`, no chip by design) — and tell Fix in the delivery that the clip came out without a presenter, because the swap changes the style he ordered. Only then suspect the prompt. `logs/clip-log.jsonl` gets no row for a run Fix calls off; state file records it (see step 9 / abort rule). **Localize an image-driven refusal by DIFFING the chip sets across attempts:** keep the failing attempt's images, drop one, submit again — whatever is common to BOTH failing sets is the suspect, which narrows the hunt to one crop instead of to the prompt, the presenter or the project. **The START FRAME belongs in that diff: it is an attached image too, and it is the one element a multi-scene run adds that the passing single-scene run never had — a frame carrying the presenter is a person-bearing reference even when every product crop is clean, so for a chained scene N+1 the cheapest retry is to drop the CHARACTER chip and keep the start frame (the frame already shows the presenter; the frame-only resubmit passed on the first try), and only then crop or drop the frame itself.** **A refusal whose MESSAGE changes between attempts is a different signal, not a retry cue** — several rapid submits in one sitting can surface a new `Failed` wording (an unusual-activity / browser-extension note), so pause (~10 min) instead of resubmitting immediately. And **only the card's own `You will be refunded` line proves a refund**: a Failed card without it leaves the credit state unreadable — report it as unreadable, never as charged and never as free. **A `Failed` card whose text carries YOUR product name is proof the submit reached the agent** — capture it before any reload (the reload drops the row); after that do not read the same run's post-reload prompt-absence as the NO-TRACE tell, which only applies when no such card was ever seen.
- **Two different 'Settings' controls, do not confuse them:** `[aria-label="Settings trigger"]` opens the inline panel (aspect tiles + model picker + "Generating will use N credits") — in the narrow layout this is where you switch to Video, and at desktop width the SAME panel has come up as the full video panel (Frames/Ingredients, 16:9|9:16, 360p|720p, 4/6/8/10 s plus the credits line). Read the panel you actually got instead of assuming image-only: if a `mat-button-toggle-checked` sits on a duration or resolution group, it is already in video mode and its "Generating will use N credits" line is the cost of the clip you are about to submit. **Settings persist per project — but DURATION does not reliably track the current order:** a return visit often opens the panel already on an earlier clip's terms (9:16 · 720p · 8 s, credits line live), so aspect and resolution can be right while the seconds are stale. Read every term, click the duration tile that matches THIS order (4/6/8/10 s) even when nothing else needs changing, then re-read the credits line — it must move with the duration (Omni Flash 720p ≈ 1.5 cr/s: 8 s → 12, 10 s → 15), and that movement is the only proof the tile took. Esc without changes only when aspect, resolution AND duration all match the order. `[aria-label="Settings"]` (tune icon) opens the **"Agent settings" drawer**, which is where video generation is actually persisted: "Confirm before generating" (Always/Never), "Image generation default", **"Video generation default"** (aspect 16:9/9:16, x1–x4, `Omni 1.1 Flash`), and a **Save** button — it is a form, so set 9:16 + Omni there and Save before submitting
  - **More than one element carries `aria-label="Settings"` — pick by RECT before clicking.** A TOP-BAR gear (`y < 60`) and the prompt-bar `tune` (`y ≈ 1400`, bottom) coexist, and the top-bar one opens either the agent instructions/session panel (tens of thousands of chars of history — the stale-instruction text lives there) or the **View mode menu** (Grid/Batch, Grid size, Sound on hover, Return silent videos, Show tile details, Clear prompt on submit), not the video defaults you were reaching for. Filter the matches on `getBoundingClientRect().y > 500` to reach the prompt-bar control; never take `querySelector`'s first match.
  - **That menu leaves a transparent `.cdk-overlay-backdrop` over the viewport and it does NOT clear on Escape** (keydown dispatched on `body` or on `document` alike). From then on every `elementFromPoint` on a prompt-bar control returns the backdrop DIV, so `Start generation` / `Settings` / the picker trigger all read as broken buttons. One line fixes it — `document.querySelectorAll('.cdk-overlay-backdrop').forEach(e=>e.remove())` — restoring hit-testing while preserving every chip (the menu container itself is `pointer-events:none`; only the backdrop blocks). Hit-test for an overlay before re-parenting a button or reloading, same as for `flow-loading-page`.
  - **Verify the selected tile by class, not by reading the text**: the drawer renders every option label (`16:9 4:3 1:1 3:4 9:16`…) regardless of which is active. The chosen one carries `mat-button-toggle-checked` on its outer `mat-button-toggle` (and `aria-pressed="true"` on the inner button). Read that back after clicking.
  - **The drawer can survive Save and swallow the submit.** `Save` writes the setting but does not always dismiss the panel, and while it is open a click aimed at `Start generation` lands on a stray `MAT-ICON` instead — no confirm card, no credits spent, and it reads as 'the button is broken'.   - **Neither control may exist.** A run can come up with NO `[aria-label="Settings trigger"]` at all (`no-btn`) while the gear opens only the agent session panel — that is not a blocker and not a bug to chase: state aspect / duration in seconds / resolution / Thai voiceover explicitly in the prompt (see the stale-instruction pitfall) and the clip comes out on those terms. Do not burn rounds hunting a settings panel this layout does not render; open one only to read the live credit cost. The same verdict applies when the trigger IS in the DOM but reports a 0×0 rect: `click_at_xy` on its centre clicks (0,0) and does nothing, so treat a zero-size settings control exactly like a missing one.   - **Do NOT gate on `document.body.innerText` no longer containing `Agent settings`** — `flow-agent-panel` keeps that markup in the DOM long after the drawer stopped being interactive, so the check stays true forever while the bottom `flow-prompt-box` editor is already live (Esc and the drawer's own Close/Back never cleared it). The gate that works is hit-testing the control you are about to press: `document.elementFromPoint(cx, cy).closest('button')` must return that button — its own `mat-icon` child is fine. If it returns a page-level element, dispatch the pointer sequence on the panel header control `flow-agent-panel button[aria-label="Close"]`, which slides the panel in and restores the live prompt box, then re-read its rect. Never retry Start generation blindly on a miss — a submit that lands twice costs double.
- 'Return silent videos' OFF; 'Clear prompt on submit' ON → chips cleared after send. Both live in the View mode menu, whose text lists EVERY option regardless of state — read each switch's state from its own class (`mat-mdc-slide-toggle-checked` / `mdc-switch--checked` on the toggle beside the label), never from the label's presence.
- One scene ≈ 8–10 s; each scene is billed separately at the rate in Trigger phrases, so longer scenes and higher resolution both cost more — read the panel's figure rather than assuming a fixed rate. Longer = more scenes then cut in editor; never 'Always approve'
- **'Start generation' is the one control the JS dispatch sequence does NOT fix** — unlike the picker buttons, dispatching on it reports ok and does nothing. It needs a real `click_at_xy` on the point where it is PAINTED: find that point by visual hit-test, since its rect can lie. Re-parenting is a last resort because it can trigger an `unusual activity` rejection (step 5). Treat 'dispatch returned ok' as no evidence of a click; always read back a state change.
- The session history scrolls in its own container; scrollIntoView on the prompt box doesn't move it (the prompt is fixed outside the scroller) — find the element with `scrollHeight > clientHeight+200` that contains the session text and set `scrollTop = scrollHeight` to reach the newest cards
- Build every dynamic JS expression by json.dumps() interpolation from Python — a bare Python variable inside the expression throws ReferenceError at eval time. **`js()`'s SECOND positional argument is a target/session id, NOT a JS argument: `js(expr, someString)` dies with `No target with given id found` before a line of JS runs, which reads like a dead tab rather than a signature mistake — always interpolate the value into the expression (`js(expr % json.dumps(name))`) and keep `js()` to a single argument.** **Never put JS object literals inside a Python f-string either**: the `{...}` braces are parsed as Python expressions and the whole call dies with a bare `NameError` before any JS runs, which reads like a broken control rather than a quoting bug — build the payload by string concatenation (or json.dumps) and hand it to `js()` intact. And when concatenating a function INTO an expression, parenthesize it before calling it — `((el)=>{…})(b)`; `JSON.stringify((el)=>{…}(b))` is a `SyntaxError: missing ) after argument list` at parse time, which reads like a broken control rather than a malformed expression. The same parser error hits NESTED ARROW chains inside one `js()` call (e.g. a `MutationObserver(muts=>{muts.forEach(m=>m.addedNodes.forEach(n=>{…}))})` one-liner) — for any multi-statement snippet, prefer an `(function(){…})()` IIFE built with `var`, which the wrapper never mangles — but do NOT nest that IIFE inside another callback in the SAME call: an IIFE inside a `.map()` body inside `JSON.stringify(...)` comes back as `SyntaxError: Unexpected end of input`, which reads like a broken page rather than a length limit. Hoist the IIFE to a top-level `var` helper first, or split the read across two `js()` calls. A long comma-joined `querySelectorAll` selector carrying several quoted attribute selectors trips the same wrapper bug on legal JS — it comes back `SyntaxError: missing ) after argument list` and loses the whole read — so split any wide DOM probe into two or three small IIFE calls with one selector each instead of one mega-query. **Never let a Python string escape reach a regex literal inside `js()`**: `"\n"` in a non-raw Python string becomes a real newline, a newline inside `/…/ ` is a parse error (`SyntaxError: Invalid regular expression: missing /`), and that reads like a broken control — use `indexOf()` / `split()` / `String.fromCharCode(10)` instead of regex, or write the expression as a raw string. **And `js()` already parses JSON-shaped returns into Python dict/list** — wrapping that result in `json.loads()` raises `TypeError: … not str, not list`; use the object directly. **Never %-format a template that holds JS either** (`'…%s…' % js`, `JS_TPL % i`): a literal `%` inside the JS — a regex such as `/(\d+)%/` or a percent readout — is parsed as a conversion spec and Python aborts with `ValueError: unsupported format character` before any JS runs, which reads like a broken page rather than a quoting bug. Inject with `.replace('IDX', json.dumps(value))`, and quote what you inject: an unquoted `i:first` substitution is a `ReferenceError` at eval time — but only `.replace()` a template you have first assigned to a VARIABLE: chaining `.replace('PLACEHOLDER', …)` onto a chain of concatenated string literals replaces it in the LAST literal alone, so a placeholder sitting in the first one survives and the expression dies with `SyntaxError: missing ) after argument list`, which reads as broken DOM instead of a broken template. **And never `.replace()` a SHORT identifier that also occurs as a JS identifier in the same string** — substituting numbers into a snippet whose parameters are literally `cx, cy` via `.replace('cx','160')` rewrites the PARAMETER LIST too, yielding `(function(160,228){…})` and a `SyntaxError: Unexpected number` that reads as a broken page rather than a broken substitution. Put the literal values in the template when you write it, or inject a uniquely-prefixed placeholder (`__CX__`). And `print()` every helper return — a bare `page_info()` as a call's last line comes back as empty output.
- Wrong-tab symptom: 'no-btn'/'no-back' on Flow controls means the queries hit another tab (an external link switches the active tab, and a freshly relaunched profile also RESTORES stale tabs — e.g. a leftover Shopee login page) — check `page_info()` and goto_url back to `https://flow.google.com/project/<id>` before any Flow DOM work.     - **A `Something went wrong` Failed card is not a verdict on the prompt, the product or the account, and submits can die this way several times in a row.** Each failed attempt charges nothing (credits never move), so the remedy is the same deliberate resubmit every time: re-attach image + character, retype the prompt, submit again, and repeat until one lands. **This repeat-until-it-lands rule does NOT cover the `We noticed some unusual activity` card.** That card is a bot or rate signal: check the browser UA first (`HeadlessChrome` means relaunch headful), and on a submit burst stop after one retry. Both cases are covered in `references/flow-browser-env.md` → `unusual activity`. Keep exactly ONE submit in flight at a time — waiting for the verdict before the next attempt — because a retry issued while an earlier one is still pending is the only way this loop costs double. **When it is always the FIRST submit of a run that dies, plan for it as the normal path**: budget the extra chip-attach cycle and the ~1 min confirm-before-resubmit into the run, and never go hunting for a defect in the prompt, the chips or the layout on the strength of one Failed card — nothing about them differs between the submit that died and the one that lands.
  - **Third stalled-run tell: NO TRACE — your prompt never becomes a chat bubble.** Prompt cleared, yet after the first `Page.reload` your prompt text is absent from the DOM entirely (not in any `flow-chat-bubble`, not in `body.innerText`) — **and, on that same reloaded page, no grid tile carries your prompt or the agent's rewrite of it.** Check the tile BEFORE reading the absence of chat surfaces: an agent-mode start can render ONLY as a grid card (`play_circle` + the agent's REWRITE as its body — an English structured restatement naming product and presenter, NOT your prompt's opening words, so test that text for your PRODUCT NAME) with no chat bubble, no `a2ui-surface` and no confirm card ever appearing, so "prompt cleared + nothing in chat" on the live DOM is an unresolved verdict, not a failed send — one reload resolves it. Only when the prompt text AND that tile are both absent after the reload does this tell apply — and it stays absent across several reloads, which is a send that never registered server-side, not a slow render: polling cannot resolve it. Wait one full poll cycle (~10 min of short reloads) to be sure, then RESUBMIT deliberately with the same recipe (re-attach image + character, retype, submit ONCE) and say in the report that the first attempt left no trace. **Cheapest early reading: on the live DOM your prompt becomes a new `flow-chat-bubble` within seconds of the click — its presence confirms the run is real; its absence is only a cue to reload once and read the grid tile, never a verdict on its own.**
