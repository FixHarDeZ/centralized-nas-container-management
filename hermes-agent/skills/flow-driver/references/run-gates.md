# Run gates — file-proof, order-proof and run-state checks (steps 5–9)

Always-on gates that catch a wrong file, a wrong claim, an unregistered submit or a broken rotation before delivery. Each rule states its mechanism so it can be applied without re-deriving it.

## Step 7 — downloading

- **Prove the opened tile is THIS clip before spending anything on it: the editor renders your own prompt verbatim.** Opening the newest tile lands on `/edit/<id>`, and the page body starts with the exact head of the prompt you submitted (a raw-prompt echo, not the agent's rewrite), so a first line that matches your prompt's opening words is the cheapest positive ID there is — cheaper and more specific than a generic auto-title like "Woman reviewing game disc", which the auto-titler produces for any game clip. If the id is also absent from `/opt/data/clips/flow-state/<project-id>.json` → `known_edit_ids`, append it.

- **The fast path is a HOST gate, not a `<video>`-exists gate.** Only `currentSrc` values on `flow-content.google/video/<uuid>?…` are fetchable files; a `currentSrc` on `flow.google.com/asb/…` is a player handle — `curl -sL` of it writes a truncated body that `ffprobe` rejects with `moov atom not found`. Read the URL BEFORE curling: an `asb` src ending `=s512-…` is a thumbnail rendition, so it is wrong by construction, not truncated. Run `ffprobe -v error -show_entries format=duration <file>` immediately after EVERY curl; on failure delete the partial and go straight to the Download media menu. Never re-curl the same URL: the URL shape, not the download attempt, is what was wrong.
- **`Download media` may exist only inside the editor's top-bar `More options` menu, not as a toolbar button.** When the toolbar renders Back / Show asset info / More options / Done editing and an `[aria-label="Download media"]` query returns nothing, the control is not missing: `click_at_xy` the top-bar `More options` (y < 60), hit-test with `document.elementFromPoint(x,y).closest('[role=menuitem]')`, `click_at_xy` the `Download media` item — then expect the quality list as a SECOND menu (`270p`/`720p`/`1080p`/`4K`, matched on `.label`) needing one more `click_at_xy` on `720p`. Verdict = a new file by mtime across BOTH download dirs (the `Downloading your video…` / `downloaded!` toast is optional — it has been absent on a download that landed fine). A missing toolbar control is never the signal to jump to the signed-URL capture rungs.

## Step 8 — proving the file

- **Copy a downloaded file into the other Downloads dir under its EXACT source basename.** `verify-clip.py` hashes every `.mp4` in both dirs and ignores only a byte-identical copy sharing that basename, so a renamed copy hashes as an `earlier clip` and exits 1 against your own download. Read the `dupes` array: if it names the file you just copied from, delete the renamed copy and re-copy under the original name — that is a self-collision, not a duplicate clip.
- **Read EVERY occurrence of an on-screen date, not just the clearest one.** One render can carry a correct date on one beat and a wrong one on another (right year late, wrong year early), so zoom-check each occurrence against the brief separately. Two reads agreeing on one frame prove only what that frame shows, never that the frame matches the brief — agreement validates the transcription, not the claim.

## Steps 9 / queue mode — ordering

- **The clip-log row is the gate between clip N's verify and clip N+1's submit.** Drafting clip N+1's prompt while clip N renders is the right use of the wait window, but defer its `hook_id` pick — and every prompt line that depends on the hook — until clip N's row exists, because the hook LRU reads `hook_id` from the log. Writing the whole queue's rows at the end is exactly how the least-recently-used rule silently fails and the last-used hook repeats across consecutive posts.
- **State writes ride the same gate:** `last_character_used` in `/opt/data/clips/flow-state/<project-id>.json` is what excludes a face from the next pick, so update it per clip as you log, not once for the queue — otherwise two clips in one sitting can land the same presenter.
- **A queue never absorbs the per-clip frame check.** Each clip is judged on its own pixels: extract, vision-check and log clip N before its delivery goes out, even when clip N+1 is already rendering.

## Step 9 — chained multi-scene: when NOT to submit scene N+1 early

Default is overlap (submit scene N+1 while Fix reviews scene N) because he dislikes slow runs. **Override the overlap when your own frame check of scene N already found reportable defects** — hold scene N+1's submit until Fix rules on scene N (2026-10-31, two runs in one sitting):
- คลิปโฟร์โมสต์: scene 1 มี defect ปกกล่องเพี้ยนทุกเฟรม → Fix สั่ง "เลิกทำคลิปนี้" → scene 2 ที่ chain ค้าง render ถูกทิ้งทั้งเครดิต
- คลิปไฟแช็คพลาสม่า: เก็บ scene 1 ส่ง review ก่อน ไม่กด scene 2 จนเขาพิมพ์ "ผ่าน" → ไม่มีอะไรถูกทิ้ง

Mechanism: scene N+1 starts from scene N's last frame, so re-gen'ing scene N silently invalidates scene N+1. Say it in the review message ("scene 2 ยังไม่กด submit — รอคำสั่ง เพื่อไม่ให้เครดิตทิ้งฟรี") and offer the fast-out ("chain เลย") if he prefers speed over credits.

## Step 5 — proving the submit registered

- **Test for your own prompt TEXT in `document.body.innerText`, never for a chat bubble.** This layout renders no `flow-chat-bubble` at all — the count stays 0 across a perfectly live submit — so a bubble selector reports "no trace" on a run that is real, and the remedy it triggers (wait a full poll cycle, then resubmit) wastes that cycle. The submitted prompt instead lands in the media grid as a batch entry: `span.text-part` → `DIV.prompt-text` → `FLOW-EXPANDABLE-PROMPT` → `FLOW-BATCH-INFO` → `.batch-container`, whose text carries your prompt verbatim, with the agent's grid card sitting above it. Probe `document.body.innerText.indexOf(<a phrase only you wrote>) >= 0`; it finds the prompt in either shape and in either order. Presence = the send registered. Absence after ONE reload is still only a cue to read the grid tile, never a verdict on its own.
- **A probe that TIMES OUT is not a probe that returned nothing — settle the renderer before reading any result as "no trace".** `Runtime.evaluate` timing out (5–60 s, `document.readyState` included) means that page's renderer is wedged, not that your selector missed; the same call succeeding on a fresh `about:blank` tab (`js('1+1')`) proves the harness and browser are alive and isolates the break to that page, so navigate the WORKING tab back to the project instead of closing targets in a loop. Only an eval that COMPLETES with an empty answer counts toward a no-trace verdict.
- **An agent bubble reading `error / Failed to render response` is NOT a failed render** — it is a streaming/UI glitch in the agent's own reply and says nothing about the video: a generation card behind it can finish normally. Judge a stall only by a `.error-title` `Failed` row, a session `Failed` card, or no new `/edit` id across two reloads; resubmitting on that text alone while the first render is still live is how one order double-charges.
- **An asset attached to a submitted generation drops OUT of the picker's `Uploads` list, and the list — not the Search box — is the verdict.** Search returning `No assets found.` for a filename you saw listed minutes earlier is the consumed-asset signature, not a query bug: clear the search and compare the unfiltered list against what you remember. Re-upload the same local file (no re-upload of anything else, no reload — a reload would cost every chip) and carry on; three re-queries of a gone file buy nothing.

## Abort close-out — including a PARTIAL cancel

- **The cancel can keep the scenes already reviewed and drop only what is left ("ไม่ทำต่อ scene 2").** Same close-out as a full abort — no `/opt/data/clips/logs/clip-log.jsonl` row (that log is the record of what shipped), record it under `aborted_run` in `/opt/data/clips/flow-state/<project-id>.json` with every `edit_id` you actually opened, the reason, and `logged: false`; kill Chrome as the last act; report spend with any figure you never read left as "unreadable" — PLUS two things a full abort does not need: hand over the two copy blocks from steps 10–11 (hashtags, basket link) for the clip already in his hands, because that clip is now the finished deliverable, and name the CTA gap, since the multi-scene rule writes the CTA wording ONLY into the final scene's prompt, so a cut-down single-scene clip carries no on-screen and no spoken CTA at all. Offer the re-gen as his call — it spends credits — and say plainly that the cancelled scene's render may still finish server-side rather than implying it stopped.

## Credit questions — gates before spending
- **Never write a spending default INTO the question text.** A `clarify` that ends with `ไม่ตอบ = ทำต่อ scene 2` promises a purchase for silence, and a future run inherits two conflicting promises (the written default vs. the zero-spend rule). State what each option costs, let silence resolve to zero spend, and execute the no-spend path without re-asking — a clip is never generated on the strength of an answer he did not give.
- **The wrap-up that asks only for the posting assets (`จบงานดีกว่า ขอ hashtag และปักตะกร้า`) is a close-out, not a request to finish the run**: hand over the two fenced blocks from steps 10–11 immediately, write the `state` note for whatever actually shipped, kill Chrome as the last act, and submit NO remaining scene. Ending a run is not a command to complete it.
